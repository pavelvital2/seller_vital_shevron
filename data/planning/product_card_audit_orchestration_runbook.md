# Product Card Audit Orchestration Runbook

Дата создания: 2026-06-25

## Статус

Предварительная согласованная схема массовой работы с карточками Vital
Shevron. Схема описывает подготовку слоя 2 `data/catalog/card_audits/` через
одноразовых fresh-агентов-аудиторов и fresh-агентов-проверяющих под
управлением оркестратора.

Это не apply-контур и не разрешение на изменение карточек Ozon/WB.

## Минимальный пакет документов для fresh-агентов

Чтобы не перегружать контекст одноразовых агентов, оркестратор передает им
не весь проектный набор runbook-ов, а компактный пакет:

```text
data/planning/card_audit_agent_docs/README.md
data/planning/card_audit_agent_docs/card_auditor_minimal_prompt.md
data/planning/card_audit_agent_docs/card_validator_minimal_prompt.md
data/planning/card_audit_agent_docs/card_audit_minimal_rules.md
data/planning/card_audit_agent_docs/card_audit_output_contract.md
```

Полные runbook-и остаются источником истины для оркестратора. Fresh-аудитор и
fresh-проверяющий должны получать только минимальные документы своей роли,
контракт результата и входной пакет конкретной карточки.

## Цель

Подготовить проверенные аудиты карточек для быстрого просмотра владельцем:

- HTML для владельца;
- JSON-аудит слоя 2 для проекта, пакетных правок, task-runner и будущего
  Telegram-бота;
- общий индекс/дашборд для навигации, фильтров, групп проблем и готовности к
  owner review.

Целевой объем: все карточки из карточного backlog/content master. На момент
фиксации схемы в работе было 710 карточек, 68 карточек уже прошли ранний аудит
по предыдущему процессу. Перед массовым запуском фактические цифры нужно
перепроверить по текущему `content_master`, `card_audit_packages` и
`card_audits`.

## Роли

### Оркестратор

Оркестратор управляет процессом, но не подменяет аудитора и проверяющего.

Обязанности:

- готовит единый prompt аудитора;
- готовит единый prompt проверяющего;
- готовит чеклист качества;
- формирует входной пакет одной карточки из слоя 1;
- перед SEO-аудитом готовит централизованный `seo_query_pack`: top-50 таблицы
  запросов Ozon/WB с периодом, частотностью/популярностью, источником и
  временем выгрузки, целевую разметку запросов по ролям и, если доступно,
  parser-позиции по конкретным запросам как baseline/monitoring;
- проверяет, что в карточный пакет передаются строковые SEO-данные
  `seo_query_pack.confirmed_query_rows`, а не только агрегаты
  `ozon_frequency_sum`/`wb_frequency_sum`. Каждая строка должна содержать
  `query`, `marketplace`, `role`, `seed_query`, `rank`, `frequency` или
  `popularity`, `period`, `source`, `collected_at`;
- проверяет статусы `seo_query_pack` перед выдачей карточек аудиторам:
  `ready` можно отдавать в работу, `ready_broad_only` отдавать с явным
  ограничением "точного спроса нет", `needs_manual_review` сначала уточнять
  вручную, `excluded_non_patch_assortment` не отдавать аудиторам шевронного
  контура;
- при генерации audit packages исключает из массового потока все строки со
  статусами `needs_manual_review` и `excluded_non_patch_assortment`. Такие
  строки сохраняются в `excluded_package_index.csv/json` с причиной, но
  fresh-аудиторам не выдаются до отдельного решения владельца;
- задает формат выходных файлов;
- назначает карточку fresh-агенту-аудитору;
- принимает результат только после валидации;
- формирует общий индекс;
- агрегирует batch-группы будущих правок;
- останавливает поток при системной ошибке prompt-а, схемы, данных или
  качества.

### Агент-аудитор

Один fresh-агент-аудитор получает одну карточку и после завершения больше не
используется.

Вход:

- пакет карточки из слоя 1 `data/catalog/content/`;
- все фото и/или HTML/коллаж фото;
- текущие поля Ozon;
- текущие поля WB;
- parser/SEO/signals, если доступны;
- карточный блок `seo_query_pack`, если нужны спросовые SEO-рекомендации.
  Генератор `card-content-audit-packages` берет latest
  `data/catalog/content/seo_query_pack/card_seo_targets.json` или явно
  переданный `--seo-query-pack-path` и кладет в `audit_package.json` только
  SEO-кластер конкретной карточки. Fresh-аудитор не должен ходить в ЛК
  Ozon/WB за запросами; запросы и частотность собирает оркестратор до запуска
  аудитора. Для первичного заполнения карточки основной вход - целевой
  SEO-кластер, а parser-позиции используются для контроля результата после
  изменений. Если `confirmed_query_rows` есть и релевантны карточке, аудитор
  не должен ставить SEO-статус `partial` только из-за того, что отдельный
  priority CSV содержит агрегированные суммы;
- `data/planning/product_card_fill_template_runbook.md`;
- `data/planning/card_content_standards_runbook.md`;
- `data/planning/product_card_work_runbook.md`;
- `data/planning/product_card_data_layers_runbook.md`;
- schema результата слоя 2.

Выход:

- `audit.json` слоя 2;
- HTML для просмотра владельцем;
- рекомендации `сейчас -> рекомендую -> почему`;
- итоговый готовый вариант карточки;
- batch-группы будущих пакетных изменений;
- флаги риска и неуверенности;
- список данных, которые агент не смог подтвердить.

Агент-аудитор не имеет права:

- готовить apply;
- писать в слой 3 `master_passport`;
- менять карточки Ozon/WB;
- придумывать факты, размеры, материалы, смысл изображения, SEO-данные или
  причины ошибок;
- смешивать Ozon и WB attributes в один общий список.

### Агент-проверяющий

Fresh-агент-проверяющий получает результат аудитора и проверяет соответствие
всем требованиям. После проверки агент больше не используется.

Проверяет:

- все ли фото просмотрены и описаны;
- есть ли текущее состояние карточки;
- есть ли рекомендации `сейчас -> рекомендую -> почему`;
- есть ли итоговый готовый вариант карточки;
- соблюдено ли название до 60 символов;
- описание до 2000 символов и из трех блоков;
- правильно ли рассчитаны вес, упаковка, комплектность;
- корректно ли разделены материал и состав;
- указан ли ТН ВЭД `5810999000`, если товар входит в согласованную группу;
- не смешаны ли Ozon и WB поля;
- учтены ли SEO/parser данные без нерелевантного keyword stuffing;
- группировка отмечена как отдельная dangerous write operation;
- HTML читается на мобильном и десктопе;
- JSON валиден по schema слоя 2;
- нет apply, dry-run apply или записи в слой 3.

HTML-проверка должна быть не только текстовой. Проверяющий или оркестратор
обязан открыть HTML в браузере после последней правки, посмотреть мобильный
`390x844` и десктопный `1366x1000` viewport, проверить отсутствие
page-level горизонтального overflow (`scrollWidth == clientWidth`) и только
после этого отправлять файл владельцу.

Если результат не соответствует требованиям, проверяющий возвращает список
замечаний на доработку. После доработки результат должен проверять новый
fresh-агент-проверяющий.

## Выходной HTML

HTML должен быть удобен для владельца на ноутбуке и телефоне.

Если HTML отправляется владельцу в Telegram как отдельный документ, он должен
быть самодостаточным: ключевой коллаж и критичные изображения нужно встраивать
в HTML через `data:image/...;base64,...` или отправлять файл в архиве вместе с
изображениями. Относительные ссылки вида `src="photo_collage.jpg"` допустимы
для локального просмотра в проекте, но не для одиночного Telegram-документа:
Telegram передает HTML без соседних файлов, поэтому фото не откроется. Коллаж
фото также желательно отправлять отдельным изображением в чат.

Название файла использовать по внутреннему артикулу, если он есть:

```text
<internal_sku>.html
```

Если внутреннего артикула нет, использовать безопасный fallback:

```text
<internal_product_id>.html
```

Структура HTML:

1. Верхний блок:
   - внутренний артикул;
   - Ozon/WB native IDs;
   - тип товара;
   - наличие на площадках;
   - статус проверки;
   - основные риски.
2. Фото:
   - коллаж всех фото;
   - подписи, что изображено на каждом фото;
   - что подтверждено фото;
   - чего не хватает.
3. Текущее состояние карточки:
   - Ozon title/description/attributes/photos/hashtags/grouping;
   - WB title/description/characteristics/photos/tags/grouping;
   - размеры, упаковка, вес, материал, состав, ТН ВЭД.
   - ссылки на карточки в ЛК Ozon/WB, если они известны;
   - все заполненные параметры карточки из snapshot/API: для Ozon все
     текущие attributes и служебные поля dimensions/weight/model_info, для WB
     все characteristics и служебные поля dimensions/sizes/barcodes.
4. Рекомендации:
   - таблица или блоки `сейчас -> рекомендую -> почему`;
   - флаги `confirmed`, `needs_owner_review`, `not_confirmed`;
   - batch-группы будущих правок.
5. Итоговый готовый вариант карточки:
   - `canonical_title`;
   - `ozon_title`;
   - `wb_title`;
   - `canonical_description`;
   - `ozon_description`;
   - `wb_description`;
   - целевые размеры, упаковка, вес;
   - материал/состав;
   - Ozon attributes;
   - WB attributes;
   - SEO/hastags/tags;
   - группировка как рекомендация, без apply.

Рекомендованное описание в HTML показывать визуально тремя отдельными
абзацами/блоками. Не добавлять в продающее описание размеры упаковки и вес:
эти значения должны быть в параметрах карточки, паспорте товара и отдельной
таблице рекомендаций.
6. Блок решения владельца:
   - `да`;
   - `нет`;
   - `поменять ...`;
   - `отложить`;
   - `дизайнеру`;
   - `ручная проверка`.

Допускается один адаптивный HTML вместо отдельных desktop/mobile HTML, если он
реально удобно читается на телефоне и на десктопе. Если удобство не
подтверждено, делать отдельные версии:

```text
<internal_sku>_desktop.html
<internal_sku>_mobile.html
```

## Выходной JSON

HTML нужен владельцу, JSON нужен проекту. Каждый аудит должен иметь машинный
слой:

```text
audit.json
```

Минимальные разделы:

- `identity`;
- `source_refs`;
- `visual_audit`;
- `current_state`;
- `recommendations`;
- `proposed_final_card`;
- `seo`;
- `media`;
- `grouping`;
- `batch_groups`;
- `risks`;
- `not_confirmed`;
- `validator_status`;
- `owner_review_status`.

JSON хранится в слое 2 и не является owner-approved паспортом.

## Индекс и дашборд

Оркестратор должен вести общий индекс:

- карточка;
- internal SKU;
- статус `queued/audited/validation_failed/validated/owner_reviewed`;
- пути к HTML/JSON;
- типы проблем;
- batch-группы;
- приоритет;
- наличие рисков;
- нужен ли дизайнер;
- готовность к owner review.

После накопления пачки индекс должен позволять быстро видеть:

- карточки с плохими названиями;
- карточки без 5 полезных фото;
- карточки с неверной упаковкой/весом;
- карточки с разным Ozon/WB смыслом;
- товары, которые есть только на одной площадке;
- группы для пакетных изменений.

## Параллельность

Параллельный запуск допустим, но только после пилота.

Рекомендуемый порядок:

1. Пилот на 5 карточек.
2. Разбор качества prompt-а, HTML, JSON и проверки.
3. Пачка 20 карточек.
4. После стабильного качества - параллельные потоки.

Нельзя запускать все оставшиеся карточки сразу, пока prompt аудитора,
validator prompt и schema не проверены на пилоте. Ошибка в инструкции может
размножиться на сотни HTML.

## Quality Gate

Карточка считается готовой для просмотра владельцем только если:

- audit HTML создан;
- audit JSON создан;
- проверяющий агент подтвердил соответствие требованиям;
- оркестратор добавил строку в общий индекс;
- статус карточки `validated`;
- нет блокирующих `not_confirmed`, которые делают итоговый вариант карточки
  недостоверным.

Если блокирующие `not_confirmed` есть, карточку нельзя считать готовой к
быстрому owner review. Ее нужно вынести в отдельный список ручной проверки.

## Правило улучшения схемы

Если в процессе работы обнаружено слабое место схемы, повторяющаяся ошибка,
лишний ручной шаг, недостающая проверка, возможность автоматизации,
оптимизации, ускорения или снижения риска, агент обязан сразу сообщить об
этом владельцу.

Сообщение должно содержать:

- что именно не работает или может быть улучшено;
- где это проявилось;
- риск, если оставить как есть;
- предлагаемое изменение схемы;
- нужно ли обновить runbook, skill, schema, prompt или CLI;
- можно ли продолжать текущую пачку без остановки.

Если улучшение подтверждено и полезно, агент должен обновить профильный
runbook, `data/planning/recommendations_index.md`, skill при необходимости и
краткую память Hermes без секретов.

## Следующий технический шаг

Перед массовым запуском нужно подготовить:

1. `auditor prompt`;
2. `validator prompt`;
3. точную schema `audit.json`;
4. HTML-шаблон;
5. генератор входного пакета одной карточки из слоя 1;
6. индекс/дашборд;
7. пилот на 5 карточек.

Только после успешного пилота масштабировать процесс на оставшиеся карточки.
