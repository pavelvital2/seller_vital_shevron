# Product Card Fill Template Runbook

Дата создания: 2026-06-25

## Назначение

Это согласованный владельцем шаблон целевого заполнения карточки Vital
Shevron. Он используется как основа для слоя 3 `master_passport` и будущих
marketplace-specific dry-run на Ozon и WB.

Шаблон не является разрешением на изменение карточек. Любые правки карточек,
фото, характеристик, группировки, названий или описаний выполняются только по
цепочке:

```text
read-only -> dry-run -> review -> approved -> apply -> verify -> result
```

## Место в карточном контуре

Шаблон применяется так:

```text
Layer 1: data/catalog/content/
  исходные данные Ozon/WB

Layer 2: data/catalog/card_audits/
  аудит агента: сейчас -> рекомендую -> почему

Layer 3: data/catalog/master_passport/
  согласованный владельцем финальный паспорт товара по этому шаблону
```

Нельзя формировать marketplace write dry-run напрямую из слоя 1 или из
несогласованного результата слоя 2.

## Шаблон карточки

### 1. Идентификация

Обязательные поля:

- `internal_sku` - внутренний артикул Vital Shevron;
- тип товара: `шеврон`, `нашивка`, `петлицы`, `комплект`;
- Ozon: `offer_id`, `product_id`, `sku`, если товар есть на Ozon;
- WB: `vendorCode`, `nmID`, `barcode`, если товар есть на WB;
- наличие на площадках: `ozon_only`, `wb_only`, `ozon_wb`;
- текущая и целевая группировка;
- комплектность: количество физических изделий и состав комплекта.

Marketplace-native ID нельзя менять при заполнении паспорта. Внутренний
артикул хранится отдельно в `internal_sku`.

### 2. Название

На первом этапе название единое:

```text
canonical_title = ozon_title = wb_title
```

Ограничение: максимум `60` символов.

Базовая структура:

```text
Тип изделия + способ крепления + тематика/структура + место ношения
```

Примеры структуры:

```text
Шеврон на липучке МВД нарукавный
Нашивка пришивная СВО на кепку
Петлицы ФСИН на липучке
```

Размер не добавлять в название по умолчанию, если он уже есть в
характеристиках, инфографике, описании и паспорте. Размер можно добавить
только если он нужен для различения вариантов, группировки или подтвержденного
SEO-спроса.

Название не должно быть списком ключевых запросов. Главный критерий:
понятность покупателю, соответствие фото и точное попадание в релевантный
поиск.

### 3. Описание

На первом этапе описание единое:

```text
canonical_description = ozon_description = wb_description
```

Ограничение: максимум `2000` символов.

Структура из трех блоков:

1. Описание товара: что изображено, тематика/структура, форма, где носить и
   для чего подходит.
2. Из чего и как сделан товар: материал, состав, вышивка, крепление,
   комплектность, обработка края и качество.
3. Краткий блок о магазине Vital Shevron: современное оборудование,
   качественная вышивка, опытный коллектив и качественные материалы без
   неподтвержденных заявлений.

Описание не должно подменять характеристики, но должно естественно включать
важные поисковые формулировки, если они релевантны товару.

Размеры упаковки, вес с упаковкой и marketplace-specific размеры упаковки
нельзя вставлять в продающее описание как отдельную фразу вида "Упаковка для
карточки: ...". Эти данные должны быть в параметрах Ozon/WB, master passport и
таблице рекомендаций `сейчас -> рекомендую`. В описании можно упоминать только
покупательски значимую комплектацию, например наличие ответной части липучки.

В HTML-аудите рекомендованное описание показывать визуально тремя отдельными
абзацами/блоками, чтобы владелец сразу видел структуру текста.

Для массового заполнения комплектов позывных `мох` по owner-approved шаблону
`Турист` использовать согласованную нейтральную фразу:

```text
меньший шеврон дополнен тематическим изображением
```

Эта фраза заменяет индивидуальное описание картинки на малом шевроне только
для данной шаблонной пачки. Она не разрешает придумывать изображение и не
отменяет обязательный фото-аудит для новых шаблонов, одиночных карточек,
спорных товаров или карточек с непроверенным фотосетом.

### 4. Материал, состав и крепление

Материал и состав различать:

- материал товара: `Габардин`, если товар действительно из габардина;
- состав товара: `полиэстер, нейлон`.

Для шевронов и петлиц:

- крючковая часть липучки пришита с обратной стороны;
- мягкая ответная часть липучки входит в комплект.

Для нашивок:

- липучки нет;
- нашивка пришивается.

Если конкретное поле состава отсутствует в схеме площадки, состав фиксировать
в описании и отдельно отмечать это в аудите/маппинге.

Описание в целевом паспорте и в карточках Ozon/WB должно быть написано от
лица производителя для покупателя. Оно описывает сам товар, материалы,
крепление, комплектность, назначение и производство. Нельзя переносить в
описание язык аудита или источник проверки: `на фото видно`, `по инфографике`,
`карточка показывает`, `подтверждено snapshot/API`, `по текущей карточке`.
Такие формулировки используются только в аудиторских пояснениях,
`not_confirmed`, причинах рекомендаций и технических блоках HTML.

Для тематических неформенных шевронов, которые не являются ведомственными или
форменными, не использовать `на рукав` в едином названии и не делать на этом
акцент в хештегах/тегах. В описании можно оставить рукав как один из вариантов
крепления наряду с бронежилетом, рюкзаком, сумкой и экипировкой. Для
ведомственных и форменных шевронов `на рукав` в названии допустимо, если это
реальное назначение. Для шевронов на кепку `на кепку` в названии обязательно.

### 4.1. Marketplace-specific параметры

Для пачного заполнения использовать не общий список всех возможных параметров
маркетплейса, а карту реальных полей редакторов:

```text
data/planning/product_card_editor_field_map_runbook.md
```

Базовые значения для текущего ассортимента:

- Ozon `ТН ВЭД коды ЕАЭС`: `5810999000 - Прочие вышивки из прочих текстильных
  материалов`;
- Ozon `Количество в упаковке, шт` и `Единиц в одном товаре`: количество
  физических изделий `1`/`2`/`3`/`4`/`5`; петлицы = `2`;
- Ozon `Целевая аудитория`: `Взрослая`;
- Ozon `Вид выпуска товара`: `Фабричное производство`;
- Ozon `Страна-изготовитель`: `Россия`;
- Ozon `Количество заводских упаковок`: рабочая рекомендация `1`, подтвердить
  dry-run перед apply;
- WB `Вид декора для одежды`: `шеврон`, `нашивка` или `петлица`;
- WB `Состав`: `полиэстер; нейлон`;
- WB `Страна производства`: `Россия`;
- WB `ТНВЭД`: `5810999000`;
- WB `Количество предметов в упаковке`: `1 шт.` / `2 шт.` / `3 шт.` /
  `4 шт.` / `5 шт.`, петлицы = `2 шт.`;
- WB `Комплектация`: `шеврон на липучке N шт.`, `нашивка без липучки пришивная
  N шт.`, `петлица на липучке 2 шт.`;
- WB `18+`, `Нужна маркировка КИЗ`, `Подтверждаю КИЗ`: false/unchecked для
  обычных карточек.

Поля других WB/Ozon-предметов, которые не относятся к шевронам, нашивкам,
петлицам или комплектам, в аудит и пачное заполнение не включать.

### 5. Размеры, вес и упаковка

Размер изделия указывать как:

```text
ширина*высота мм
```

Размер упаковки указывать как:

```text
ширина*высота*толщина мм
```

Для WB размеры упаковки переводятся в сантиметры.

Базовые правила упаковки:

| Тип товара | Ozon упаковка | WB упаковка |
| --- | --- | --- |
| Нарукавный шеврон | `100*100*10 мм` | `10*10*1 см` |
| Шеврон на кепку | `100*60*10 мм` | `10*6*1 см` |
| Нагрудный шеврон | `130*50*10 мм` | `13*5*1 см` |
| Шеврон на спину | `300*100*10 мм` | `30*10*1 см` |
| Петлицы, 1 товарная единица | `100*40*10 мм` | сначала `10*4*1 см`, fallback `10*5*1 см`, затем `10*6*1 см` |

Комплекты:

```text
длина/ширина упаковки = максимальные длина/ширина среди изделий комплекта
толщина упаковки = количество физических изделий * 10 мм
```

Петлицы:

- 1 товарная единица = две неразрезанные петлицы;
- размер самих петлиц: `80*30*5 мм`;
- в упаковке считать как один физический слой толщиной `10 мм`.

Вес:

| Изделие | Вес |
| --- | --- |
| 1 обычный шеврон | `10 г` |
| 1 нашивка | `10 г` |
| 1 товарная единица петлиц | `10 г` |
| 1 наспинный шеврон | `30 г` |

Для комплектов вес суммируется по количеству физических изделий.

### 6. Классификация

Для шевронов, нашивок, петлиц и комплектов из этих товаров использовать:

```text
5810999000 - Прочие вышивки из прочих текстильных материалов
```

Если появится новое подтвержденное исключение по категории или товару, его
нужно отдельно согласовать с владельцем и зафиксировать в профильном runbook.

### 7. Фото

Минимальный целевой набор для карточки, если товар позволяет:

1. Главное фото товара целиком.
2. Фото или инфографика размера.
3. Обратная сторона, липучка или комплектация.
4. Вариант ношения.
5. Сервисная инфографика по материалу, вышивке, комплектности или упаковке.

Если информация уже есть на инфографике, нельзя считать ее отсутствующей.
Отдельное чистое фото можно рекомендовать как улучшение, но не как исправление
ошибки отсутствия информации.

Для аудита агент обязан посмотреть все фото, определить количество фото, что
изображено на каждом фото, основные цвета, фон/камуфляж, форму и размер
изделия.

### 8. Цвет и название цвета

Цвет товара:

- указывать все заметные цвета на изделии;
- порядок цветов: от самого большого заполнения к меньшему;
- первый цвет обычно фон шеврона.

Название цвета:

- короткое название шеврона или варианта;
- используется для различения товаров в группе;
- должно быть понятно покупателю при наведении на вариант в группе.
- должно идентифицировать конкретный шеврон внутри группы, а не повторять
  название группы. Например, если группа `БПЛА`, то для конкретного шеврона
  корректнее `Смерть сходящая с небес, хаки`, а не `БПЛА хаки`.

### 9. SEO

SEO-блок паспорта должен содержать:

- релевантные ключевые запросы;
- текущую видимость по parser-данным;
- поисковые запросы Ozon/WB из ЛК/API;
- Ozon-хештеги до лимита `30`;
- WB теги/поисковые поля, если они доступны в текущей схеме;
- запрещенные/нежелательные слова;
- обоснование, какие запросы включены в название, описание, хештеги или теги.

SEO-блок должен разделять:

- `content_terms` - слова, подтвержденные карточкой, фото и характеристиками;
- `seo_demand_terms` - релевантные запросы с частотностью/популярностью из
  ЛК Ozon/WB, parser или другого зафиксированного источника спроса.

Сбор спросовых SEO-источников выполняет оркестратор до запуска карточных
аудиторов. Fresh-аудиторы не должны самостоятельно ходить в ЛК Ozon/WB за
поисковыми запросами и частотностью. Во входной пакет аудитора нужно передавать
`seo_query_pack`: top-50 таблицы Ozon/WB за выбранный период с источником и
временем выгрузки, целевую разметку запросов по ролям и, если доступно,
parser-позиции по конкретным запросам.

На первом проходе карточки оптимизируются не под все частотные запросы подряд,
а под целевой SEO-кластер: широкий базовый запрос + точная тематика/структура
+ место ношения, если оно релевантно. Parser-позиции на этом этапе
используются как baseline и будущий контроль движения после изменений, а не
как обязательная основа первичного названия и описания.

Логика приоритета для первичного заполнения:

1. Главный точный запрос карточки: например `шеврон ФСБ`, `шеврон БПЛА`,
   `шеврон Шторм`.
2. Релевантный широкий запрос: `шеврон`, `шеврон на липучке`, `нашивка`,
   `петлица`.
3. Место ношения, если оно соответствует товару.
4. Запросы, по которым товар уже виден в parser, использовать для контроля и
   последующей корректировки после накопления данных.

Название не перегружать ключами. Основную семантику распределять между
названием, описанием, характеристиками, хештегами/тегами и фото.

Если есть только агрегат parser без конкретных запросов, например количество
видимых запросов и лучшая позиция, нельзя готовить SEO-расширение названия,
описания, WB tags или Ozon hashtags. В этом случае статус SEO-рекомендации:

```text
blocked_no_query_list
```

Частотные релевантные запросы из ЛК можно подмешивать в название и описание
только после проверки, что запрос соответствует товару, фото и характеристикам
и что во входных данных есть marketplace, период и частотность/популярность.

### 10. Площадочные поля

В паспорте хранить раздельно:

```text
canonical_title
ozon_title
wb_title
canonical_description
ozon_description
wb_description
ozon_attributes
wb_attributes
```

На первом этапе значения `canonical`, `ozon` и `wb` для названия и описания
совпадают. Позже Ozon/WB версии можно расширять отдельно только как
согласованную SEO-оптимизацию.

Ozon и WB характеристики нельзя сводить в один общий список: разные ID,
единицы, обязательность, типы значений и API-поля.

## Автоматизация приведения карточек к шаблону

Рекомендуемая автоматизация должна идти не сразу в apply, а через безопасный
pipeline.

### Этап 1. Template Validator

CLI-команда проверяет каждую карточку слоя 1 against template:

- название: длина, структура, наличие типа/крепления/темы/места ношения;
- описание: три блока, длина, материал/состав/крепление;
- размеры/вес/упаковка по типу товара и комплектности;
- ТН ВЭД;
- фото: количество и роли фото;
- цвет/название цвета;
- SEO: хештеги, теги, parser visibility, релевантные запросы;
- группировка: текущая и целевая.

Результат сохраняется в слой 2 как audit result и группируется по типам
массовых правок.

### Этап 2. SEO Candidate Builder

Отдельная команда собирает для каждого товара SEO-кандидаты:

- top-50 запросов Ozon из ЛК/API с периодом и частотностью/популярностью;
- top-50 запросов WB из ЛК/API с периодом и частотностью/популярностью;
- целевой SEO-кластер карточки:
  `primary_target`, `secondary_target`, `broad_identity`, `placement`,
  `exclude`;
- parser-запросы, где товар уже виден: конкретный запрос, marketplace,
  native ID товара, позиция и run id/время сбора, если эти данные доступны;
- частотность Ozon-хештегов;
- запреты и слова, которые площадка не принимает;
- текущие позиции и конкурентов, если данные доступны.

Выход: не готовый apply, а рекомендации:

- какие слова включить в название;
- какие оставить в описании;
- какие вынести в Ozon-хештеги;
- какие использовать как WB теги/поисковые элементы;
- какие не использовать из-за риска нерелевантности или блокировки.

Если для карточки нет списка конкретных запросов, builder должен вернуть
`blocked_no_query_list`, а не подбирать SEO-слова из текущего названия под
видом поискового спроса.

### Этап 3. Passport Draft Generator

Команда создает черновик слоя 3, но со статусом `owner_review_needed`.

Она берет:

- исходники слоя 1;
- аудит слоя 2;
- правила шаблона;
- SEO-кандидаты;
- owner-approved internal SKU;
- marketplace schemas Ozon/WB.

Результат:

- `draft_master_passport`;
- сравнение `сейчас -> предлагаю`;
- список массовых групп: названия, описания, упаковка, материал/состав,
  фото, хештеги, группировка;
- HTML для согласования владельцем.

### Этап 4. Owner Review Dashboard

HTML-дашборд для владельца:

- фильтр по типу проблемы;
- фильтр по маркетплейсу;
- фильтр по типу товара;
- карточка товара с коллажем фото;
- `сейчас -> рекомендую -> почему`;
- кнопочная/табличная логика решений: принять, отклонить, изменить текст,
  отправить дизайнеру, отложить.

После согласования только принятые решения попадают в слой 3.

### Этап 5. Marketplace Dry-Run Builder

Из слоя 3 формируются отдельные dry-run пакеты:

- Ozon: title, annotation, attributes, hashtags, media, grouping;
- WB: title, description, characteristics, media, grouping.

Dry-run должен показывать:

- что изменится;
- какие поля не меняются;
- какие поля нельзя заполнить из-за отсутствия API/параметра;
- какие карточки требуют ручного ЛК;
- какие изменения опасны и требуют отдельного подтверждения.

### Этап 6. Apply только после подтверждения

Apply разрешен только после review владельцем конкретного dry-run пакета.

После apply обязательно:

- verify через API/ЛК;
- отчет `было -> стало`;
- обновление инструкций при внештатных ситуациях;
- обновление слоя 1 свежими данными после применения.

## Рекомендованный порядок запуска автоматизации

1. Реализовать сохранение audit result в слой 2.
2. Реализовать `template-validator` без write-операций.
3. Реализовать `seo-candidate-builder`.
4. Реализовать генерацию draft passport по шаблону.
5. Сделать HTML owner-review dashboard.
6. Только после этого делать marketplace-specific dry-run builder.
7. Apply реализовывать последним и только по safety-цепочке.

## Риски

- Автоматически сгенерированное название может стать менее релевантным, если
  слепо резать до 60 символов без parser/поисковых данных.
- SEO нельзя оптимизировать только по частотности: запрос должен точно
  соответствовать товару и фото.
- Фото-аудит нельзя заменить счетчиком фото: агент должен смотреть сами
  изображения.
- Ozon/WB поля отличаются, поэтому единый паспорт не означает один общий
  payload для двух площадок.
- Группировка является отдельной опасной операцией и не должна смешиваться с
  массовой заменой описаний или характеристик.
