# Supply Planning Runbook

## Ozon stock schema 2026-07-31

Для `/v4/product/info/stocks` актуальный признак схемы остатка находится в
`stocks[].type` (`fbo`/`fbs`). Поле `stocks[].source` поддерживать только как
fallback для старых snapshot. Если при ненулевом каталоге расчёт возвращает
нулевой FBO-остаток, такой запуск считать недействительным и сначала проверить
схему live-ответа; нулевую стоимость владельцу не сообщать.

Дата: 2026-06-13

## Назначение

Read-only расчет поставок Ozon/WB на основе остатков, продаж за 90 дней или за
квартал, среднесуточных продаж, региональной локализации спроса и ограничений
производства.

Цель - сформировать предварительный список:

- что произвести;
- в каком количестве;
- на какой маркетплейс;
- в какой целевой кластер/регион отправить товар;
- сколько производственных дней потребуется.

## Safety

Расчет поставок является read-only/dry-run операцией.

Создание, изменение или отмена поставки, изменение остатков, бронирование
слотов, отправка коробов/паллет и любые действия в ЛК считаются опасными
write-операциями и требуют цепочки:

```text
read-only -> dry-run -> review -> approved -> apply -> verify -> result
```

Нельзя создавать поставки или менять остатки без явного подтверждения
владельца.

## Бизнес-правила Vital Shevron

- Основной период анализа: последние `90` полных дней.
- Допустимый альтернативный период: квартал, если владелец явно просит квартал.
- Производство считается в физических шевронах, а не в товарных единицах и не
  в комплектах.
- В текущей производственной модели в поставку "в работу" включать только
  шевроны, нашивки, петлицы и комплекты из них.
- Головные уборы, подсумки, панамы, фартуки, фальшпогоны и другие товары,
  которые сейчас не изготавливаются, исключать из производственного плана и
  выносить в отдельный review/исключенный список.
- Одна закладка шьет минимум `8` физических шевронов одного производственного
  артикула.
- Общее количество по каждому производственному артикулу должно быть кратно
  `8` физическим шевронам.
- Минимальное количество товарных единиц по одному артикулу в поставке - `8`
  шт. Это относится и к комплектам позывных из `2` шт.: минимальная поставка
  такого артикула также `8` комплектов, а производственная нагрузка равна
  `8 * 2 = 16` физических шевронов.
- Товарные единицы поставки и производственная нагрузка в шевронах считать
  отдельно.
- Петлицы: две видимые петлицы вышиты одной неразрезанной парой и считаются
  одним физическим изделием. Для производственной нагрузки и исторического
  количества поставок `1 товарная единица петлиц = 1 физическое изделие`,
  `pack_qty=1`; надпись `2 шт.` в старом marketplace-title не означает две
  отдельные производственные единицы.
- Текущая производственная мощность: `200` физических шевронов в день.
- Рабочий цикл поставок: `5` дней производство -> отгрузка -> следующий
  `5`-дневный цикл.
- Производственная мощность одного цикла: `1000` физических шевронов.
- До увеличения производственных мощностей план следующей поставки должен
  загружать полный цикл на `1000` физических шевронов, а не останавливаться на
  минимальной расчетной потребности.
- Минимальную расчетную потребность закрывать первой; оставшуюся мощность
  цикла распределять по приоритетным артикулам с учетом спроса, покрытия,
  маржинальности, актуальности карточек и уже запланированных отгрузок.
- Предварительный целевой запас, если владелец не задал другой горизонт:
  `30` дней.
- Критичный запас: меньше `7` дней продаж.
- Низкий запас: меньше `14` дней продаж.

Эти горизонты являются рабочими допущениями для первого расчета. Их можно
изменить после согласования владельцем.

## Источники Ozon

API-first источники:

- `POST /v4/product/info/stocks` - общий FBO/FBS остаток по product_id/SKU.
  В ответе Ozon тип склада может приходить в поле `type` (`fbo`, `fbs`), а
  не в поле `source`; при разборе нужно учитывать оба варианта. Если считать
  только `source`, FBO-остаток может ошибочно стать `0` по всем товарам.
- `POST /v2/analytics/stock_on_warehouses` - остатки по FBO-складам:
  `warehouse_name`, `free_to_sell_amount`, `reserved_amount`.
- `POST /v3/posting/fbo/list` - FBO posting-и за период с
  `analytics_data.city`, `analytics_data.warehouse_name`, product `sku`,
  `offer_id`, `quantity`, `price`.

Важное ограничение:

- `POST /v3/posting/fbo/list` принимает `limit` не больше `100`. При сборе
  90 дней нужно идти по cursor до конца.

Ozon `/v1/analytics/data` можно использовать для проверки продаж по SKU, но
на 2026-06-13 региональная dimension через него не подтвердилась. Для
локализации Ozon использовать FBO posting analytics: город покупателя и склад
отгрузки. Если нужен областной/окружной разрез, сначала исследовать ЛК/API и
зафиксировать источник.

API источники заявок на поставку Ozon:

- `POST /v1/supply-order/status/counter` - количество заявок по статусам;
- `POST /v3/supply-order/list` - список `order_ids` по состояниям заявок;
- `POST /v3/supply-order/get` - пачка заявок с `order_number`, `state`,
  `drop_off_warehouse`, `timeslot`, `supplies[]`, `supply_id`, `bundle_id`,
  `macrolocal_cluster_id`;
- `POST /v1/supply-order/details` - детальная карточка одной заявки,
  `supply_state`, `content.bundle_id`, `storage_warehouse`;
- `POST /v1/supply-order/bundle` - состав товаров по `bundle_id`: `offer_id`,
  `sku`, `product_id`, `barcode`, `quantity`, `name`, пагинация через
  `limit/last_id`.
- `GET /v1/supplier/available_warehouses` - загруженность складов Ozon.

Live-уточнение 2026-07-14:

- `/v3/supply-order/list` возвращает `order_ids/last_id` на верхнем уровне;
- `/v3/supply-order/get` возвращает `orders[]` на верхнем уровне;
- `/v1/supply-order/bundle` принимает `bundle_ids[]`, `limit <= 100` и
  возвращает `items/last_id/has_next` на верхнем уровне;
- пагинация списка заявок идет через `last_id`, не через `offset`.

Для исторического подсчета физических изделий период определять по
`orders[].created_date` Ozon и `createDate` WB в часовом поясе владельца.
Даты приемки, фактической поставки и отгрузки для выбора месяца не
использовать. Ozon-заявки с `order_tags.is_virtual=true` не считать отдельной
физической поставкой: они повторяют часть состава исходной заявки, указанной
в `original_supply_id`, и без исключения дают двойной счет.

Endpoint-карточка: `data/reference/api_docs/ozon/endpoints/supply_order.md`.
Локальная копия официального Swagger:
`data/reference/api_docs/ozon/openapi/seller_swagger_20260629.json`.

Проверка 2026-06-29: прямой shell-доступ к Ozon docs возвращал redirect loop,
но через CDP/ЛК Vital Shevron официальная документация и Swagger открылись с
`HTTP 200`. Для постоянного кода использовать строковые enum OpenAPI, а не
числовые значения из ранних live-проб.

Официальные статусы для `filter.states`, `orders[].state` и
`supplies[].state`: `DATA_FILLING`, `READY_TO_SUPPLY`,
`ACCEPTED_AT_SUPPLY_WAREHOUSE`, `IN_TRANSIT`,
`ACCEPTANCE_AT_STORAGE_WAREHOUSE`, `REPORTS_CONFIRMATION_AWAITING`,
`REPORT_REJECTED`, `COMPLETED`, `REJECTED_AT_SUPPLY_WAREHOUSE`, `CANCELLED`,
`OVERDUE`. В `details.supplies[].supply_state` также есть
`ACCEPTED_AT_STORAGE_WAREHOUSE`.

Официальные `sort_by` для `/v3/supply-order/list`: `ORDER_CREATION`,
`ORDER_STATE_UPDATED_AT`, `TIMESLOT_FROM_UTC`, `TIMESLOT_FROM_LOCAL`.
`sort_dir`: `ASC`, `DESC`.

`POST /v1/supply-order/timeslot/get` официально устаревает и должен быть
отключен 2026-08-19; для будущей реализации изучить
`/v2/supply-order/timeslot/list`.

## Источники WB

API-first источники:

- `GET /api/v1/supplier/stocks` - текущие остатки по складам.
- `GET /api/v1/supplier/orders` - заказы и отмены за период.
- `GET /api/v1/supplier/sales` - продажи/возвраты за период.

API источники складских поставок WB/FBW:

- `POST https://supplies-api.wildberries.ru/api/v1/supplies` - список
  поставок FBW;
- `GET https://supplies-api.wildberries.ru/api/v1/supplies/{supplyID}` -
  статус, склад, количество, приемка, принято к продаже;
- `GET https://supplies-api.wildberries.ru/api/v1/supplies/{supplyID}/goods` -
  состав товаров: `vendorCode`, `barcode`, `nmID`, `quantity`,
  `acceptedQuantity`, `readyForSaleQuantity`;
- `GET https://supplies-api.wildberries.ru/api/v1/supplies/{supplyID}/package` -
  короба/упаковки и количество по баркодам.

Endpoint-карточка: `data/reference/api_docs/wb/endpoints/fbw_supplies.md`.

Важно: `GET https://marketplace-api.wildberries.ru/api/v3/supplies` относится
к другому контуру поставок и не является источником складских FBW-поставок. На
2026-06-28 он вернул `0` активных, хотя FBW API и ЛК показывали активные
поставки.

Поля для локализации:

- `regionName` - регион покупателя;
- `oblastOkrugName` - федеральный округ/крупный региональный слой;
- `warehouseName` - склад, с которого шла продажа.

Ограничение:

- `GET /api/v1/supplier/stocks` отключен WB 23.06.2026. Для текущих остатков
  использовать `POST https://seller-analytics-api.wildberries.ru/api/analytics/v1/stocks-report/wb-warehouses`,
  агрегируя `quantity` по размерам и складам одного `nmId`.
- Для свежей поставки со статусом `statusID=4` (`Идет приемка`) складской
  `stocks-report` может не отражать поставку синхронно. В ответе владельцу
  нужно отдельно показывать данные FBW Supply API: `quantity` (отгружено),
  `acceptedQuantity` (принято), `readyForSaleQuantity` (готово к продаже) и
  `unloadingQuantity` (разгружается). Эти значения нельзя складывать с
  `stocks-report.quantity`: источники могут пересекаться и обновляться в разное
  время. Финальный продаваемый остаток повторно проверять после `statusID=5`.
- На live-проверке 2026-07-18 поле `inWayFromClient` во время приемки также
  включило входящую FBW-поставку, хотя в ЛК оно подписано `В пути от
  покупателя`. По Электростали `313` из `401` единицы совпали по всем `23`
  `nmId` вчерашней поставки, еще `3` единицы этих же товаров были
  `inWayToClient`; сумма `313 + 3` совпала с `acceptedQuantity=316`. Поэтому
  `inWayFromClient` нельзя целиком считать возвратами покупателя без сверки с
  `/supplies/{supplyID}/goods`.
- Историческая сверка того же инцидента исключила трактовку оставшихся `88`
  единиц как массовых возвратов. Срез 2026-07-17 21:30 по Электростали:
  `quantity=383`, `inWayFromClient=22`, `inWayToClient=1`, всего `406`.
  Свежий срез 2026-07-18: `quantity=9`, `inWayFromClient=401`,
  `inWayToClient=3`, всего `413`. WB переместил почти весь объем между
  техническими состояниями при почти неизменной общей товарной массе. Это
  нельзя считать возвратами; точная причина без транзакционного движения WB не
  подтверждена. Возможная связь с незавершенной приемкой и временной
  приостановкой склада является только гипотезой.
- Для поставок WB не использовать `/api/v3/supplies` как основной источник
  inbound на склады; использовать `supplies-api.wildberries.ru`.

## API-first и fallback в ЛК

Если API не дает нужные данные по текущим поставкам, статусам, приемке,
кластерам размещения, складам приемки или составу поставки, агент обязан идти
в ЛК Ozon/WB, а не останавливать расчет на неполных API-данных.

Сначала нужно читать официальную документацию Ozon/WB API, OpenAPI/Swagger или
уже реализованный проектный адаптер. Подбор payload/enum/endpoint допустим
только если документация недоступна, отсутствует, явно устарела или
противоречит фактическому API; причину такого перехода нужно записать в
отчет/артефакт запуска. Подбор не должен выполнять write-операции.

Обязательный порядок:

1. Найти и прочитать официальную документацию/API-схему или проектный адаптер.
2. Зафиксировать, какой API-метод проверен и чего в нем не хватило.
3. Открыть правильный проектный ЛК/профиль согласно `AGENTS.md`.
4. Сохранить безопасный LK snapshot без секретов: номера поставок, статус,
   дата, склад/кластер, количество товаров, количество принято/в пути.
5. Если ЛК показывает активную поставку, а API возвращает `0` активных
   поставок, в отчете писать расхождение `API != LK` и использовать ЛК как
   актуальный источник статуса.
6. Состав поставки по артикулам нельзя домысливать из общей суммы. По Ozon
   сначала брать `/v1/supply-order/bundle` через `bundle_id`, по WB -
   `/api/v1/supplies/{supplyID}/goods`. Если API недоступен или не дал состав,
   брать детальную LK-выгрузку или ранее созданный owner-approved файл, если
   совпали маркетплейс, кластер/регион, количество и дата/номер поставки. Если
   состав не подтвержден, строку выносить в ограничение: "состав поставки не
   подтвержден".
7. При расчете следующей поставки вычитать confirmed inbound из потребности:
   `готово к отгрузке`, `на точке отгрузки`, `в пути`, `приемка`,
   `отгрузка разрешена`, `идет приемка`.

## Отчет по остаткам и активным поставкам Ozon

С 2026-07-18 штатный task `ozon-stock-supply-monitor`, CLI-команда с тем же
именем и Telegram-кнопка `Ozon -> Остатки и поставки Ozon` строят свежий
read-only отчет. Остатки или поставки в кабинете не меняются.

Отчет разделяет три источника:

1. Общий FBO `present/reserved` из `/v4/product/info/stocks`.
2. Складской `free_to_sell_amount/reserved_amount/promised_amount` из
   `/v2/analytics/stock_on_warehouses`.
3. Незавершенные supply-order и их bundle-состав из цепочки
   `/v3/supply-order/list -> /get -> /details -> /bundle`.

Правильная сверка остатков:

```text
general_fbo_present = warehouse_free_to_sell + warehouse_reserved
```

Сравнивать `present` только с `free_to_sell` нельзя: разница может полностью
состоять из резерва и не является рассинхроном. `promised_amount` показывается
отдельно и не прибавляется к активным supply-order, поскольку источники могут
описывать одну поставку.

В отчет включаются состояния `DATA_FILLING`, `READY_TO_SUPPLY`,
`ACCEPTED_AT_SUPPLY_WAREHOUSE`, `IN_TRANSIT`,
`ACCEPTANCE_AT_STORAGE_WAREHOUSE`, `REPORTS_CONFIRMATION_AWAITING`,
`REPORT_REJECTED`, `OVERDUE`. Подтвержденным inbound до завершения приемки
считаются только `READY_TO_SUPPLY`, `ACCEPTED_AT_SUPPLY_WAREHOUSE`,
`IN_TRANSIT`, `ACCEPTANCE_AT_STORAGE_WAREHOUSE`. Заявки на стадии актов могут
уже пересекаться с продаваемым остатком и не должны повторно вычитаться в
планировании.

Заявки с `order_tags.is_virtual=true` исключаются из количественных итогов как
дубли исходной поставки. Для каждой обычной поставки состав подтверждается
через `bundle_id`; количество физических изделий считается по подтвержденному
`pack_qty`. Если `storage_warehouse` еще не назначен, показывается
`macrolocal_cluster_id`, а не выдуманное название склада.

Артефакты: Markdown для Telegram, CSV по складам, товарным строкам и активным
поставкам, raw API snapshots, summary JSON и RunManifest.

## Ozon: файл `В работу`

С 2026-07-18 task и CLI `ozon-production-work-plan`, а также кнопка
`Ozon -> В работу Ozon` формируют read-only производственный Excel. Диалог
запрашивает режим `capacity|coverage_days`, значение и количество кластеров
назначения от `1` до `20`. Локальное утверждение привязано к checksum файла и
не создает поставку Ozon.

Потребность обязательно считается для каждой пары `товар x кластер`:

```text
cluster_item_need =
  weighted_daily_sales_in_cluster * target_days
  - free_to_sell_in_same_cluster
  - confirmed_inbound_to_same_cluster
```

Общие остатки и общие поставки Ozon используются только для контрольной
сверки и не уменьшают потребность отдельного кластера. `reserved_amount` и
`promised_amount` показываются справочно, но не считаются свободным остатком;
`promised_amount` не складывается с supply-order из-за возможного overlap.

Связь источников строится через официальный `/v2/cluster/list`:

- `financial_data.cluster_to` posting-а дает кластер спроса;
- `data.fulfillments[].name` связывает складской остаток с кластером;
- `macrolocal_cluster_id` связывает confirmed supply-order с тем же кластером.

Приоритет кластера равен сумме положительного дефицита товаров в физических
изделиях. Выбираются первые `N` кластеров по убыванию дефицита. В capacity
mode физический лимит не превышается; в coverage mode используется введенный
горизонт. Спрос берется за `90` полных дней с повышенным весом последних `30`.
Производственные кратности: нарукавные `8`, комплекты позывных `6` комплектов,
нагрудные `12`, наспинные `2`, на кепку `9`, неизвестный тип `8` с контролем.

Excel: `Артикулы`, `Ozon кластеры`, `Контроль`. В строках кластерного листа
отдельно показаны продажи, free stock, reserve, promised, confirmed inbound,
сырой дефицит, округленная потребность и покрытие.

Live smoke 2026-07-18 при capacity `200` и `3` кластерах выбрал Ростов,
Воронеж и `Москва, МО и Дальние регионы`; распределено `199` физических
изделий, остаток мощности `1`. Значения являются снимком и при каждом запуске
запрашиваются заново.

### Проверка артикулов в готовой Ozon-отгрузке

Для внешней кластерной книги, где в строке уже есть Ozon SKU, актуальный
артикул продавца нужно определять только по свежему `/v3/product/list`:

```bash
PYTHONPATH=src /home/Codex/agent-tools/python/bin/python \
```

- не выполняет marketplace write.

## Отчет по остаткам и активным поставкам WB

Отчет обязан включать все зарегистрированные FBW-поставки до завершения, а не
только товары на складе и поставки, по которым уже началась приемка. В
частности, статус `statusID=3` (`Отгрузка разрешена`) является активной
поставкой и всегда должен попадать в отчет.

Показатели разделять на самостоятельные блоки:

1. Доступный остаток на складах WB из `stocks-report`.
2. Поставки со статусом `Отгрузка разрешена`.
3. Поставки в пути или на точке отгрузки, если такие статусы присутствуют.
4. Поставки со статусом `Идет приемка` с отдельными полями `quantity`,
   `acceptedQuantity`, `readyForSaleQuantity`, `unloadingQuantity` и
   расчетной недостачей только после достаточных данных.
5. Недавно завершенные поставки, необходимые для сверки перехода в остаток.

Для каждой поставки показывать номер, склад, дату создания, плановую дату,
статус, количество товарных единиц WB, принято и готово к продаже. Разрешенные
к отгрузке и находящиеся на приемке количества нельзя называть доступным
остатком. Допустимо показывать справочный общий объем активного контура, но
обязательно рядом приводить разбивку по статусам. Для комплектов дополнительно
считать физические изделия по подтвержденному `pack_qty`; не смешивать этот
показатель с товарными единицами WB.

Контрольный срез 2026-07-18 подтвердил три поставки в статусе `statusID=3`:
Шушары — `136`, Волгоград — `246`, Новосемейкино — `184` товарные единицы,
всего `566`. Отдельная поставка в Электросталь в статусе `statusID=4` содержит
`318` единиц. Значения являются снимком на момент проверки и должны заново
запрашиваться при каждом отчете.

## Методика расчета

Для каждой marketplace-local позиции сначала считать потребность в товарных
единицах:

```text
avg_daily_sales = sales_period_qty / period_days
target_stock = ceil(avg_daily_sales * target_days)
raw_need = max(0, target_stock - current_stock)
recommended_supply_units = raw_need
```

Затем отдельно считать производственную нагрузку:

```text
production_article = confirmed production article / master_sku / seller SKU
chevrons_per_unit = pack_qty or confirmed bundle size
raw_chevrons = recommended_supply_units * chevrons_per_unit
production_chevrons_by_article = sum(raw_chevrons by production_article)
rounded_production_chevrons = ceil(production_chevrons_by_article / 8) * 8
production_days = ceil(total_rounded_production_chevrons / 200)
cycle_capacity = 5 * 200 = 1000 physical chevrons
```

Если товар является комплектом из `N` шевронов, производственная нагрузка равна
`товарные единицы * N`. Для комплектов из разных производственных артикулов
нужна детализация компонентов; если ее нет, строку нужно помечать как
ограничение и выносить на review.

Для постоянного цикла поставок:

```text
projected_stock_at_next_dispatch =
  current_stock + already_planned_inbound - forecast_sales_until_dispatch

next_cycle_need =
  max(0, target_stock - projected_stock_at_next_dispatch)
```

План следующего цикла должен учитывать уже готовящуюся/запланированную
поставку, прогноз продаж до даты следующей отгрузки, кратность `8` по
производственным артикулам и целевую загрузку `1000` физических шевронов на
`5` дней. Если минимальная потребность меньше `1000`, свободную мощность
нужно дозагрузить приоритетными артикулами, а не оставлять цикл неполным.

Приоритет:

- `urgent` - остаток `0` при наличии продаж или дней запаса меньше `7`;
- `high` - дней запаса меньше `14`;
- `medium` - дней запаса меньше `30`;
- `ok` - запас покрывает целевой горизонт;
- `no_sales` - продаж за период нет, производство не рекомендовать без
  отдельного решения.

## Термины складов и кластеров

В расчетах поставок нельзя подменять целевой кластер поставки складом
фактической отгрузки или складом текущего остатка.

Использовать разные поля:

- `stock_warehouse` - где сейчас лежит остаток;
- `ship_from_warehouse` - откуда маркетплейс фактически отгрузил заказ;
- `buyer_region` / `buyer_city` - регион или город покупателя;
- `destination_cluster` - куда планируем отправить товар по спросу, лимитам,
  доступным слотам и региональному плану.

Если источник дает только `warehouseName`/`warehouse_name` фактической
отгрузки, это нужно подписывать как `ship_from_warehouse`, а не как "куда
поставить".

## Распределение "куда поставить"

Предварительное распределение считать по целевым кластерам назначения. Если
подтвержденного источника `destination_cluster` нет, отчет должен явно писать
`предварительно` и показывать ограничение источника.

Допустимые источники для `destination_cluster`:

- выгруженный кластерный/региональный план поставки;
- официальный источник Ozon/WB с кластерами, складами приемки, лимитами и
  слотами поставки;
- поддерживаемый проектом mapping `buyer_region`/`buyer_city` ->
  `destination_cluster`, если он проверен на текущих правилах маркетплейса.

Склады фактической отгрузки можно использовать только как диагностический
сигнал спроса и доступности, но не как финальное направление поставки.

Для Ozon:

- `analytics_data.warehouse_name` из FBO posting-и считать
  `ship_from_warehouse`, а не `destination_cluster`;
- `analytics_data.city` использовать как сигнал географии спроса, но для
  поставки нужен mapping города/региона на целевой кластер или отдельный
  Ozon-источник по складам приемки/лимитам;
- текущие FBO-остатки по `/v2/analytics/stock_on_warehouses` использовать как
  `stock_warehouse`;
- перед реальной поставкой обязательно проверить FBO-лимиты/слоты и правила
  поставки в ЛК.

Для WB:

- `warehouseName` из продаж считать `ship_from_warehouse`, а не
  `destination_cluster`;
- `regionName` и `oblastOkrugName` показывать как географию спроса;
- для направления поставки использовать региональный план, лимиты/склады
  приемки WB или проверенный mapping региона на целевой склад/кластер;
- перед реальной поставкой обязательно проверить лимиты складов WB.
- для файлов создания поставки WB нужен `barcode` WB и количество; если во
  внешнем Excel есть только `vendorCode`/артикул продавца и количество,
  перед передачей файла владельцу нужно добавить колонку `Баркод ВБ` из
  свежего WB Content API `/content/v2/get/cards/list`. Если API временно
  недоступен, можно использовать последний `data/catalog/wb/processed/wb_catalog.csv`
  как fallback и явно указать это в отчете.

## Внешние Excel-планы поставки

Если владелец прикладывает Excel-файлы "что изготовить" и "куда отправить",

- если это уже запланированная/готовящаяся отгрузка, учитывать ее как

6. Сохранять производные CSV/JSON/MD под `data/runs/<date>/`, не коммитить

При проверке готового Ozon-плана по кластерам обязательно сверять файл с

Ошибочную предварительную версию отчета, пересобранную после исправления

## WB-кнопка `В работу`

С 2026-07-18 для WB действует отдельный read-only task
`wb-production-work-plan` и Telegram-кнопка `Вайлдберриз -> В работу`.
Старый `plan-supply-workbooks` сохраняется для совместимости, но его legacy
WB-расчет с `/api/v1/supplier/stocks`, четырьмя top-кластерами, минимумом
`200` физических изделий на кластер и единой кратностью `8` не является
источником нового WB-файла в работу.

Владелец выбирает один из режимов:

1. `capacity` - вводит доступное количество физических изделий. Расчет
   определяет дефицит до `30` дней покрытия, автоматически распределяет
   допустимые производственные блоки и не превышает введенную мощность.
2. `coverage_days` - вводит количество дней. Потребность рассчитывается
   автоматически по прогнозной среднесуточной продаже и округляется вверх по
   производственной кратности.

После значения владелец выбирает количество кластеров назначения `1..6`.
Task сначала считает положительную чистую потребность всех доступных WB-
кластеров, ранжирует их по суммарному физическому дефициту и оставляет первые
`N`. При равном дефиците выше ставится кластер с большими продажами за
последние 30 дней.

Прогноз спроса использует `90` полных дней и повышенный вес последних `30`
дней:

```text
forecast_daily = avg_daily_30 * 0.6 + avg_daily_90 * 0.4
raw_need = max(0, forecast_daily * target_days
                  - regional_sellable_stock
                  - confirmed_inbound_to_region)
```

Формула применяется отдельно к каждой паре `товар x кластер`: остаток одного
кластера нельзя вычитать из потребности другого. Общие остатки магазина
разрешены только для сверки и диагностики stockout, но не для распределения
поставки.

Если текущий общий остаток равен нулю, недавних продаж нет, но продажи за 90
дней были, нулевой спрос не предполагается: применяется как минимум
`avg_daily_90`, а строка отмечается как возможный stockout. Истории ежедневных
остатков в используемом API нет, поэтому точное количество дней отсутствия
товара без отдельного источника подтвердить нельзя.

Кратность товарных единиц одного артикула:

- нарукавные шевроны - `8`;
- комплекты позывных - `6` комплектов;
- нагрудные - `12`;
- наспинные - `2`;
- на кепку - `9`;
- тип не определен - согласованный default `8`, строка остается в плане и
  получает предупреждение классификации.

Для комплектов физическая производственная нагрузка равна
`quantity * confirmed pack_qty`. Две неразрезанные петлицы остаются одной
физической единицей (`pack_qty=1`).

Кластер назначения определяется по географии покупателя
`oblastOkrugName/regionName` и региону склада назначения. `warehouseName` из
строки продажи является складом отгрузки и не может определять назначение.
Региональный остаток берется из актуального Analytics endpoint
`/api/analytics/v1/stocks-report/wb-warehouses`; подтвержденный inbound - из
FBW Supplies API по статусам `2/3/4/6`. Статус `1` не вычитается как
подтвержденный inbound.

После смены артикула продавца исторические строки WB Statistics могут хранить
старый `supplierArticle`. Перед агрегацией продаж task обязан сопоставить
стабильный `nmId` со свежим `vendorCode` Content API. Для строки, отсутствующей
в unified catalog, разрешен fallback только на owner-confirmed
`data/catalog/mapping/ozon_wb_internal_sku_confirmed.csv` по тому же `nmID`;
по названию товар не сопоставлять.

`inWayFromClient` не считается доступным остатком. При сильной
переклассификации `quantity <-> inWayFromClient` затронутые `nmID + регион`
исключаются из автоплана и попадают на лист `Контроль`, чтобы не запустить
лишнее производство.

Excel содержит:

1. `Артикулы` - суммарное производство по артикулам;
2. `ВБ регионы` - распределение по регионам назначения, спрос, остатки,
   inbound, кратность и покрытие;
3. `Контроль` - параметры запуска, полный рейтинг кластеров и строки с
   неполными/аномальными данными.

После формирования план имеет статус `pending_owner_review`. Кнопки
`Утвердить в работу`/`Отклонить` сохраняют локальное решение, привязанное к
SHA-256 Excel. Они не создают поставку и ничего не изменяют в WB.

Live smoke 2026-07-18 `wb_production_work_plan_live_smoke_v3_20260718` в
режиме capacity `100` сформировал ровно `100` физических изделий, `86`
товарных единиц, `11` артикулов и `6` регионов. Нормализация исторического
артикула через `nmID` сократила ложные `missing_catalog_mapping` с `121` до
`1`; единственная оставшаяся строка не содержит `nmID` и подтвержденного
mapping. Текущая аномалия Электростали (`inWayFromClient=410`, `quantity=0`)
корректно исключила `50` затронутых product-region строк из автоплана.

Live smoke `wb_production_work_plan_cluster_live_smoke_20260718` после
добавления `cluster_count` при capacity `200` и `3` кластерах выбрал Южный и
Северо-Кавказский (`82` физических изделия), Дальневосточный и Сибирский

нет.

## Аудит потерь при инциденте на складе WB

Правило подтверждено read-only аудитом июльских инцидентов 2026-07-31:

1. Для общего баланса магазина допустима формула
   `остаток до + фактически принятые поставки - чистые продажи - остаток
   после`. Внутренние перемещения WB внутри одного магазина в общем итоге
   взаимно сокращаются.
2. Baseline и current должны включать одинаковые состояния WB, а поставки
   учитываются по `acceptedQuantity`, не по заявленному количеству. Продажи
   считаются чистыми: продажи минус возвраты.
3. Результат формулы является учетным дефицитом, но не обязательно физическим
   ущербом. Если WB сохраняет поврежденный или замороженный товар в складском
   остатке, баланс покажет нулевую потерю до официального списания.
4. Для отдельного склада та же формула без данных о внутренних перемещениях
   дает только предварительное отклонение. Перемещение между складами
   нейтрально для магазина в целом, но создает дефицит на складе-источнике и
   избыток на складе-получателе.
5. Ближайший складской снимок показывает только верхнюю границу товара под
   риском. Значения `inWayToClient` и `inWayFromClient` нельзя называть
   физическим остатком или подтвержденным списанием.
6. Подтвержденным уничтожением считается только построчная расшифровка WB:
   отчет категории `compensation-report`, официальный перечень утраченных
   товаров или финансовая строка с `nmId` и количеством.
   Метаданные документов проверяются через официальные read-only методы
   `GET /api/v1/documents/categories` и `GET /api/v1/documents/list` на
   `documents-api.wildberries.ru`; список нужно читать страницами по 50 строк.
   Если токен не имеет категории `Документы`, аудит продолжается по остальным
   источникам, а источник документов помечается как недоступный.
7. Агрегированная строка «Добровольная выплата...» с `nmId=0`,
   `quantity=0` подтверждает сумму компенсации, но не количество утраченных
   товаров. Отрицательное значение `deduction` является выплатой продавцу.
8. Расчет вести одновременно в товарных единицах и физических изделиях:
   `physical_items = marketplace_units * confirmed pack_qty`.
9. Для каждого склада сохранять: снимок до/около инцидента, свежий снимок,
   продажи, подтвержденные поставки, финансовые строки, документы WB и
   источник публичного статуса объекта.
10. Склады с кратковременной остановкой без подтвержденного ущерба зоне
   хранения проверять отдельно и не включать в число утраченных товаров.
