# Product Card Work Runbook

Дата создания: 2026-06-14

## Назначение

Инструкция фиксирует обязательный формат покарточной работы с карточками
товаров Ozon/WB Vital Shevron.

Любые изменения карточек, названий, описаний, характеристик, фото, размеров,
веса, упаковки или группировки являются write-опасными операциями и требуют
цепочки:

```text
read-only -> dry-run -> review -> approved -> apply -> verify -> result
```

До явного подтверждения владельца разрешены только чтение, анализ, draft и
dry-run.

## Единый content master

Для подготовки массовой работы над единым представлением товаров на Ozon и WB
использовать read-only команды:

Карточный контур разделен на три постоянных слоя:

- слой 1 `data/catalog/content/` - исходные данные Ozon/WB, generated
  индексы, snapshots и audit packages без выводов агента;
- слой 2 `data/catalog/card_audits/` - результат личного визуального,
  текстового и параметрического аудита агента по каждой карточке;
- слой 3 `data/catalog/master_passport/` - только согласованный владельцем
  окончательный вариант мастер-паспорта товара для будущих dry-run.

полноценного мастер-паспорта товара и до массового карточного аудита. Команда

- `*_schema_*` - какие параметры доступны/обязательны у площадки для

- на их основе проектируется внутренний паспорт товара и отдельные маппинги
  `ozon_attributes` / `wb_attributes`.

Если `card-content-parameter-inventory` не запускался после свежего
`fetch-card-content`, нельзя считать схему параметров актуальной для массового

для marketplace-specific dry-run. Нельзя готовить write-операцию напрямую из
generated audit package или из несогласованного аудита слоя 2.

чистого фото. Если на инфографике уже показана обратная сторона, липучка,
размеры или комплектность, в аудите фиксировать, что информация присутствует.
Отдельный чистый кадр обратной стороны, мягкой ответной части или варианта
ношения можно рекомендовать как улучшение карточки, но нельзя писать, что
информация отсутствует.

## Обязательное чтение документации ЛК перед рекомендациями

Правило владельца от 2026-06-24: перед любыми рекомендациями по карточкам
товаров агент обязан полностью прочитать и зафиксировать актуальную
документацию по заполнению карточек Ozon и WB. Документацию нужно искать в ЛК
Ozon/WB и в связанных официальных справочных разделах, доступных из ЛК.

Свежий doc-review 2026-06-24 сохранен:

```text
data/runs/2026-06-24/card_content_docs_review_20260624/card_content_docs_review_report.md
```

Постоянная краткая инструкция по применению результатов doc-review:

```text
data/planning/card_content_standards_runbook.md
```

Это gate перед следующими действиями:

- проектирование полноценного мастер-паспорта товара;
- рекомендации по названию, описанию, характеристикам, фото, хештегам/тегам;
- рекомендации по группировке;
- подготовка marketplace-specific dry-run для Ozon или WB;
- массовый карточный аудит с выводами `сейчас -> рекомендую`.

До завершения doc-review агент может выполнять только read-only сбор данных,
инвентаризацию параметров, подготовку структуры отчета и технические задачи,
которые не содержат карточных рекомендаций.

Doc-review должен сохраняться в `data/runs/<date>/<run_id>/` и содержать:

- дату и время проверки;
- marketplace: Ozon/WB;
- путь в ЛК и URL/раздел справки;
- список полностью прочитанных разделов;
- требования к названию, описанию, характеристикам, фото/медиа, цветам,
  размерам, упаковке, составу/материалу, хештегам/тегам и группировке;
- API-методы, которые подтверждают или меняют эти поля;
- ограничения, спорные места и то, что не удалось подтвердить;
- вывод: какие правила нужно учесть в master product passport,
  `ozon_attributes` и `wb_attributes`.

Старые выписки из документации можно использовать как справочный слой, но они
не заменяют свежую проверку перед текущим этапом. Если ЛК или документация
недоступны, агент обязан прямо написать: `Я не могу это подтвердить`, указать
что именно не проверено и не давать рекомендации по неподтвержденной части.

Источники `collect-card-signals`:

- Ozon stocks: Seller API `/v4/product/info/stocks`;
- Ozon sales signal: Seller API `/v2/posting/fbo/list`, non-cancelled FBO
  products за период. Это сигнал заказов/отгрузок для приоритизации, а не
  финальный финансовый отчет по выкупам;
- WB stocks: Statistics API `/api/v1/supplier/stocks`;
- WB sales signal: Statistics API `/api/v1/supplier/sales`, возвраты по
  `saleID` с префиксом `R` исключаются;
- parser visibility: latest производные CSV из прошлых parser/SEO runs,
  без копирования raw parser datasets в проект.

Если нужно проверить только parser-слой без обращения к API и без риска
лимитов, использовать:

```bash
PYTHONPATH=src /home/Codex/agent-tools/python/bin/python \
  -m seller_agent.cli collect-card-signals \
  --skip-api
```

Каждый аргумент можно передавать несколько раз. Команда распознает ключи
товара по `internal_product_id`, `internal_sku`, `offer_id`/`ozon_offer_id`,
`product_id`/`api_product_id`/`ozon_product_id`, `sku`/`ozon_sku`,
`vendorCode`/`wb_vendor_code`, `nmID`/`wb_nm_id`.

Поддерживаемые сигналы:

- продажи: `sales_units_30d`, `units_30d`, `ordered_units`, `orders`,
  `sales`, `buyouts`, `quantity_sold`;
- выручка: `sales_revenue_30d`, `revenue_30d`, `revenue`, `orders_money`,
  `sales_amount`;
- остатки: `stock_total`, `fbo_present`, `fbo_stock_at_apply`, `present`,
  `quantity`, `stock`, `available_stock`, `available_stock_count`;
- parser-видимость: `parser_best_position`, `best_position`, `position`,
  `min_position`, `queries_found_count`, `visible_queries`, `top30_count`,
  `max_query_popularity_7d`.

Сигналы добавляют поля `sales_units_30d`, `sales_revenue_30d`,
`stock_total`, `ozon_stock_total`, `wb_stock_total`, `parser_best_position`,
`parser_visible_queries`, `parser_top30_queries`,
`parser_max_query_popularity_7d`, `business_priority` и `business_reasons`.
Они нужны только для ранжирования: товары с продажами, остатком и видимостью
поднимаются выше, товары с нулевым остатком помечаются как
`blocked_by_stock`.

Команды строят:

```text
data/catalog/content/card_content_index.csv
data/catalog/content/content_master.csv
data/catalog/content/content_audit.csv
data/catalog/content/card_content_audit_backlog.csv
data/runs/<date>/<run_id>/catalog_content_master_report.md
```

Content master нужен как очередь и контрольный слой перед покарточной SEO
работой:

- `title_alignment_status` показывает, совпадают ли текущие названия Ozon/WB;
- `marketplace_presence` отделяет `ozon_only`, `wb_only` и товары на обеих
  площадках;
- `full_snapshot_status` показывает, найден ли read-only snapshot карточного
  контента по Ozon/WB;
- `ozon_photo_count`/`wb_photo_count`, `*_description_present`,
  `*_attribute_count`, `ozon_hashtags`/`wb_tags` помогают выбрать карточку для
  полноценного аудита;
- `transfer_direction` показывает кандидатов на перенос на вторую площадку;
- `content_review_priority` и `next_content_step` помогают выбрать следующий
  товар для аудита.
- `card_content_audit_backlog.csv` ранжирует карточки по причинам:
  `title_mismatch`, `marketplace_only`, `photo_lt5`, `missing_cost`,
  `ozon_hashtags_missing`, отсутствующее описание/характеристики и пропуски
  snapshot. При наличии optional signal CSV также учитываются
  `sales_positive`, `stock_positive`, `stock_zero`, `parser_top30_visible`,
  `parser_top100_visible`, `parser_visible`.

Ограничение: `fetch-card-content` считает фото по данным API, но не смотрит
изображения глазами. Content master не заменяет покарточный аудит. Перед
рекомендациями по карточке агент все равно обязан открыть все фото, описать
их и сделать коллаж по правилам ниже.

Ограничение по сигналам: optional CSV не являются самостоятельным источником
истины по продажам или остаткам. Перед финальным решением по карточке,
переносу товара, цене или рекламе нужно проверять актуальные данные через
профильный отчет/API/ЛК.

## Массовая подготовка отчетов карточного аудита

Правило владельца от 2026-06-24: практическая карточная работа не начинается с
поочередного ручного разбора первой карточки. Сначала агент готовит и
сохраняет пакет read-only отчетов по выбранной очереди карточек, затем
владелец и агент работают по одной карточке уже из сохраненного пакета.

Уточнение владельца от 2026-06-24: массовый аудит карточек выполняет агент
лично и скрупулезно. Автоматизация нужна владельцу, а не агенту: она должна
помогать видеть результаты проверки, приоритеты, группы проблем, будущие
пакетные dry-run и решения на согласование. Код может собрать источники,
коллажи, индексы и шаблон отчета, но не должен без личного просмотра агентом
считать карточку проверенной или формировать окончательные выводы.

Правильный порядок:

```text
генератор собирает источники -> агент лично проверяет карточку -> агент
сохраняет выводы -> результаты группируются для владельца -> пакетный dry-run
после согласования
```

Базовая очередь для первого массового пакета:

```text
card_content_audit_backlog.csv where business_priority = now
```

Если владелец отдельно говорит "все карточки" буквально, можно расширить
пакет до всего backlog или до всего content master, но агент обязан заранее
отметить размер пакета, ожидаемый объем артефактов и риск перегруза.

Массовый пакет должен сохраняться в `data/runs/<date>/<run_id>/` и содержать:

- индекс карточек пакета с `backlog_rank`, `internal_product_id`,
  `internal_sku`, Ozon/WB native IDs, продажами, остатками, parser-позициями и
  причиной попадания в пакет;
- отдельный report/draft по каждой карточке или стабильную структуру файлов,
  из которой можно открыть отчет конкретной карточки;
- коллажи текущих фото карточки, если фото доступны через API/snapshot;
- прочитанные текущие данные по каждой площадке: все фото, название, описание,
  характеристики/атрибуты, цвет/название цвета, размеры, вес, упаковка,
  комплектность, материал, состав, ТН ВЭД/ОКПД/ОКВЭД или аналогичные поля,
  если они есть в карточке или API;
- текущая группировка товара: Ozon `model_info.model_id/count`, WB `imtID`,
  предполагаемый `target_group_key`, риски смешения товаров и рекомендация
  `keep/split/merge/manual_review` по правилам `card_grouping_runbook.md`;
- рекомендации `сейчас -> рекомендую` по каждой карточке: отдельно общий
  смысл товара, единый контент и площадочные отличия Ozon/WB;
- список недостающих фото/инфографики для
  `data/planning/product_card_designer_tasks.md`;
- ограничения источников: что подтверждено API/parser, а что требует
  визуальной или ручной проверки.

Технический generator пакета сохраняет также
`data/catalog/content/card_audit_packages/<run_id>/`. Этот generated слой не
коммитится. Он нужен, чтобы агент мог открыть конкретный сохраненный пакет и
сделать уже настоящий визуальный аудит с рекомендациями.

## Единый паспорт товара и площадочные характеристики

Правило владельца от 2026-06-24: по каждой карточке агент обязан посмотреть
все фото, прочитать название, описание и характеристики, затем подготовить
рекомендации. Аудит не ограничивается SEO-названием: он должен проверять весь
контент товара.

Целевая модель после аудита:

```text
единый внутренний паспорт товара -> адаптированное представление Ozon
                                -> адаптированное представление WB
```

Внутренний паспорт товара хранит единые подтвержденные данные:

- `internal_product_id`;
- `internal_sku`;
- единое название товара;
- единое описание;
- тип изделия: шеврон, нашивка, петлицы, комплект;
- тематика/группа по правилам внутренних артикулов;
- форма, размер изделия, размер упаковки, вес;
- комплектность;
- цвета и краткое название цвета/варианта;
- материал, состав, липучка/способ крепления;
- ТН ВЭД/ОКПД/ОКВЭД и другие шаблонные классификаторы;
- себестоимость, если поле уже подтверждено в ценовом контуре;
- SEO-ключи, Ozon-хештеги/WB-теги и заметки по видимости;
- текущая и целевая группировка товара;
- статус фото и задачи дизайнеру.

Правило владельца от 2026-06-25 для первого этапа:

- `canonical_title`, `ozon_title` и `wb_title` хранить раздельно, но заполнять
  одинаковым значением;
- единое название должно быть до `60` символов по лимиту WB;
- базовая формула названия:
  `тип изделия + способ крепления + тематика/структура + место ношения`;
- размер не добавлять в название по умолчанию, если он есть в
  характеристиках, инфографике, описании и паспорте. Добавлять только для
  различения вариантов, группировки или подтвержденного поискового спроса;
- `canonical_description`, `ozon_description` и `wb_description` хранить
  раздельно, но на старте заполнять одинаковым значением;
- единое описание должно быть до `2000` символов и состоять из трех блоков:
  подробное описание товара; из чего и как сделан/качество; короткий блок о
  магазине;
- расширение Ozon-названия или Ozon-описания относительно базового значения
  допускается позже только как отдельная SEO-оптимизация по данным parser/ЛК и
  после согласования владельца.

Площадочные данные нельзя сводить в один общий список характеристик. У Ozon и
WB отличаются количество, названия, типы и обязательность атрибутов. Поэтому
для каждой карточки в отчете и будущей структуре данных должны быть отдельные
разделы:

```text
ozon_attributes: все обязательные и полезные атрибуты Ozon
wb_attributes: все обязательные и полезные атрибуты WB
```

Шаблонные характеристики, которые одинаковы по смыслу для большинства товаров,
нужно заполнять единообразно, но маппить в конкретные поля каждой площадки:

- материал товара: ткань габардин, лицевая часть с вышивкой нитями из
  полиэстера, с обратной стороны липучка для шевронов/петлиц;
- состав товара: полиэстер и нейлон, если это подтверждено правилами изделия;
- ТН ВЭД: `5810999000` для шевронов, нашивок, петлиц и комплектов из них,
  если категория/товар не требует отдельного уточнения;
- липучка: для шевронов и петлиц крючок пришит с обратной стороны, ответная
  мягкая часть идет в комплекте; нашивки идут без липучки и пришиваются;
- вес и упаковка считаются по правилам размеров и комплектности из этого
  runbook.

Если конкретный атрибут Ozon или WB не подтвержден API, snapshot, фото,
описанием или правилом владельца, агент не заполняет его догадкой. В отчете
такой пункт нужно пометить как `требует подтверждения` или `не могу
подтвердить`.

После согласования единый вариант сначала сохраняется в проектном контентном
слое/отчете, затем готовится marketplace-specific dry-run для загрузки на
Ozon/WB. Загружать изменения на площадки можно только после отдельного
подтверждения владельца.

## Группировка в карточном аудите

Правило владельца от 2026-06-24: группировка товара является частью полного
карточного аудита. По каждой карточке отчет должен показывать текущую группу и
рекомендованное решение по группировке.

В карточном отчете нужно фиксировать:

- Ozon: `model_info.model_id`, `model_info.count`, поле/значение, которое
  влияет на объединение карточек, если оно доступно в snapshot/API;
- WB: `imtID`, размер/состав группы, если доступно через Content API;
- целевой `target_group_key` по правилу:
  `product_family / semantic_cluster / form_factor / pack_qty / attachment / color_family / size_family`;
- решение: `keep`, `split`, `merge`, `manual_review`;
- почему решение предлагается: одинаковый товар, вариант цвета/размера,
  комплектность, разное назначение, разные ведомства/тематики, риск смешения
  отзывов или SEO;
- риск: что может измениться в SEO, отзывах, рейтинге, рекламе и поведении
  покупателя.

Группировка не применяется автоматически вместе с SEO или характеристиками.
Она остается отдельной write-опасной операцией:

```text
read-only grouping audit -> grouping dry-run -> owner review -> approved -> apply -> verify
```

Если карточка входит в проблемную группу, SEO-правки нужно проектировать с
учетом будущей группировки. Для карточек, которые нужно сначала разделить или
пересобрать в группу, отчет должен прямо помечать: `сначала группировка, потом
SEO/apply контента`.

После подготовки пакета порядок работы по отдельной карточке:

```text
saved report -> owner review -> согласованные правки -> dry-run -> approved -> apply -> verify
```

До review сохраненного отчета по конкретной карточке нельзя делать write-правки
названия, описания, характеристик, фото, группировки, цены или рекламы.

## Липучка и тип изделия

Правила владельца:

- Все шевроны и петлицы идут с липучкой велкро в комплекте.
- Крючок пришит с обратной стороны изделия.
- Петля идет в комплекте.
- Все нашивки идут без липучки и пришиваются.

Если название или текущие характеристики карточки противоречат этим правилам,
агент должен вынести это как риск и предложить корректировку на review.

Для главного фото отдельно оценивать:

Для Ozon дополнительно учитывать рекомендацию Ozon по полноте медиа: карточка

нужно вынести в отчет и добавить задачу в:

```text
data/planning/product_card_designer_tasks.md
```

Этот файл нужно проверять и обновлять ежедневно при покарточной работе:
закрывать устраненные недостатки, добавлять новые и сохранять дату проверки.

## Размеры, вес и упаковка

Размер изделия всегда указывать как:

```text
ширина*высота
```

Размер упаковки всегда указывать как:

```text
ширина*высота*толщина
```

### Вес

Базовые правила:

| Изделие | Вес |
| --- | ---: |
| 1 шеврон | 10 г |
| 1 нашивка | 10 г |
| 1 товарная единица петлиц | 10 г |
| 1 наспинный шеврон | 30 г |

Для комплектов вес суммируется по количеству изделий в комплекте.

Петлицы: 1 товарная единица - это комплект из двух неразрезанных петлиц.
Покупатель разрезает их самостоятельно.

### Упаковка

| Изделие | Упаковка Ozon | Упаковка WB |
| --- | --- | --- |
| Нарукавный шеврон | `100*100*10 мм` | `10*10*1 см` |
| Шеврон на кепку | `100*60*10 мм` | `10*6*1 см` |
| Нагрудный шеврон | `130*50*10 мм` | `13*5*1 см` |
| Наспинный шеврон | `300*100*10 мм` | `30*10*1 см` |
| Петлицы, 1 товарная единица | `100*40*10 мм` | сначала пробовать `10*4*1 см`; если WB не принимает минимальный размер, пробовать `10*5*1 см`, затем `10*6*1 см` |

Петлицы идут неразрезанным комплектом из двух штук. Размер самих петлиц в
товарной единице: `80*30*5 мм`. Для упаковки считать 1 товарную единицу петлиц
как один физический слой толщиной `10 мм`, а не как два отдельных изделия.

Для комплектов изделия лежат друг на друге:

```text
длина/ширина упаковки = максимальные длина/ширина среди изделий комплекта
толщина упаковки = количество физических изделий * 10 мм
```

Примеры комплектов:

| Комплект | Упаковка Ozon | Упаковка WB |
| --- | --- | --- |
| 2 нарукавных | `100*100*20 мм` | `10*10*2 см` |
| 2 на кепку | `100*60*20 мм` | `10*6*2 см` |
| 2 нагрудных | `130*50*20 мм` | `13*5*2 см` |
| Нагрудный + на кепку | `130*60*20 мм` | `13*6*2 см` |
| Нарукавный + нагрудный | `130*100*20 мм` | `13*10*2 см` |
| Нарукавный + на кепку | `100*100*20 мм` | `10*10*2 см` |
| Наспинный + любой малый | `300*100*20 мм` | `30*10*2 см` |
| Комплект 3 шт. | площадь по самому большому, толщина `30 мм` | толщина `3 см` |
| Комплект 4 шт. | площадь по самому большому, толщина `40 мм` | толщина `4 см` |

Перед apply на WB габариты нужно привести к сантиметрам и проверить через
dry-run/API или ЛК, что WB принимает минимальный размер упаковки для конкретной
карточки. Если WB не принимает `10*4*1 см` для петлиц, использовать следующий
fallback из правила выше.

## Описание товара

Базовая структура описания, которую владелец считает предпочтительной:

На первом этапе описание единое для паспорта, Ozon и WB, максимум `2000`
символов.

1. Блок подробного описания изделия:
   - что изображено;
   - тематика/структура;
   - где носить и для чего подходит;
   - короткий смысл изображения, если он есть;
   - для ведомственных/форменных изделий не добавлять неподтвержденные смыслы.
2. Блок "из чего и как сделан / качество":
   - материал;
   - состав;
   - крепление/липучка или пришивной формат;
   - обработка края, вышивка, комплектность и упаковка;
   - размер можно упоминать в описании, но не обязательно выносить в название.
3. Короткий блок о магазине:
   - Vital Shevron;
   - современное оборудование;
   - качественная вышивка;
   - опытный коллектив;
   - качественные материалы.

SEO-специалист/агент может предложить другой порядок или формулировку, но
должен объяснить, почему это лучше для карточки.

## Материал и состав

В характеристиках различать `материал товара` и `состав товара`.

Рабочее правило владельца:

- Материал товара: ткань `Габардин`.
- Габардин состоит на 100% из полиэстера.
- Лицевая часть изделия - ткань, на которой выполнена вышивка нитями из
  полиэстера.
- С обратной стороны шеврона/петлиц пришита липучка велкро.
- Липучка состоит из нейлона и полиэстера.
- Состав товара: `полиэстер, нейлон`.

Для нашивок без липучки не указывать липучку как крепление.

Если у конкретной категории Ozon нет отдельного атрибута `Состав`, не
придумывать его. В этом случае состав фиксировать в аннотации/описании и
отдельно указать в отчете, что отдельный атрибут состава для данной категории
не подтвержден.

## Цвет и название цвета Ozon

Для шевронов на Ozon различать:

- `Цвет товара` - все цвета, которые присутствуют на шевроне. Цвета указывать
  в порядке объема заполнения: обычно сначала фон шеврона, затем остальные
  цвета по уменьшению площади.
- `Название цвета` - короткое название шеврона/варианта. Это поле помогает
  различать товары внутри группы; при наведении покупателя на товар из группы
  Ozon показывает именно это название.

Для категории `pict0143` на 2026-06-14 через Ozon Seller API подтверждены
атрибуты:

- `10096` - `Цвет товара`;
- `10097` - `Название цвета`.

Эти ID нельзя считать вечными для всех категорий. Перед dry-run/apply по другой
категории нужно получить справочник через Ozon Seller API
`POST /v1/description-category/attribute` для текущих
`description_category_id` и `type_id`.

## Хештеги Ozon

Хештеги Ozon являются отдельным атрибутом карточки. Для категории `pict0143`
на 2026-06-14 через Ozon Seller API подтвержден атрибут:

```text
23171 - #Хештеги
```

Правила владельца и Ozon:

- в отчете по карточке обязательно показывать текущие хештеги;
- Ozon разрешает до 30 хештегов на товар;
- каждый хештег начинается с `#`;
- внутри хештега не должно быть пробелов; слова соединять нижним
  подчеркиванием;
- хештеги разделяются пробелами;
- один хештег - не более 30 символов;
- не дублировать в хештегах бренд, параметры и название товара;
- использовать только релевантные хештеги;
- `БПЛА` не использовать в хештегах Vital Shevron: владелец сообщил, что Ozon
  не пропускает этот хештег.
- Ozon позволяет использовать варианты хештегов со словами слитно и через
  нижнее подчеркивание; для релевантных поисковых запросов можно использовать
  оба варианта, если они проходят редактор карточки и не вводят покупателя в
  заблуждение.

Подбор хештегов:

1. В первую очередь включать релевантные ключевые запросы, по которым карточка
   уже видна в выдаче.
2. Запросы преобразовывать в хештеги слитно и/или через `_`.
3. Добивать список до 30 хештегов по убыванию подтвержденной частотности из
   `data/planning/ozon_hashtag_frequency_table.md`.
4. Частотность хештегов собирать из редактора карточки Ozon: при вводе
   хештега ЛК показывает выпадающие варианты и частотность. Таблицу
   обновлять не реже одного раза в месяц.
5. Если частотность не собрана или устарела, не выдавать ее как подтвержденную.

Если Ozon отклоняет отдельный хештег, агент должен зафиксировать это в отчете
по карточке и в профильной инструкции: какой хештег отклонен, где проверено,
какая замена предложена.

## Код/классификация

Для всех шевронов, нашивок, петлиц и комплектов из этих товаров использовать
ТН ВЭД:

```text
5810999000 - Прочие вышивки из прочих текстильных материалов
```

Дополнительное согласование владельца для этого значения не требуется. Если в
текущей карточке стоит другое значение, это нужно вынести в список
рекомендуемых исправлений.

## Петлицы

Петлицы всегда описывать как комплект:

- 1 товарная единица = 2 петлицы;
- петлицы идут неразрезанными;
- покупатель разрезает их самостоятельно;
- крепление: липучка велкро в комплекте, если карточка относится к петлицам
  Vital Shevron.

## Перенос карточек между Ozon и WB

В будущей работе с ассортиментом могут рассматриваться товары, которые есть
только на одной площадке: `Ozon-only` или `WB-only`. Если такой товар хорошо
продается на текущей площадке, его можно рассматривать как кандидата на перенос
на вторую площадку. Это правило фиксирует будущий подход, но не задает порядок
следующих этапов.

Перед предложением переноса агент обязан подготовить read-only оценку:

1. продажи, выкупы, возвраты, остатки и маржинальность по текущей площадке;
2. SEO-видимость и ключевые запросы по текущей площадке;
3. фото-аудит всех изображений;
4. проверку правовых, контентных и ассортиментных рисков;
5. проверку, что аналог уже не существует на второй площадке под другим
   `offer_id`/`vendorCode`.

Перенос выполнять не копированием "как есть", а через карточный dry-run:

- единый внутренний brief товара: что изображено, тип изделия, размер,
  комплектность, материал, состав, крепление, упаковка, фото и базовое
  описание;
- SEO-адаптация под вторую площадку: название, описание, ключевые слова,
  хештеги/поисковые поля и обязательные атрибуты;
- выравнивание смысла карточек Ozon/WB: название, характеристики, описание и
  фото должны быть одинаковыми по сути и максимально одинаковыми по заполнению,
  если ограничения категорий позволяют;
- явное перечисление всех различий, которые остаются из-за разных форматов
  полей Ozon и WB.

Создание новой карточки, изменение контента, фото или характеристик на второй
площадке требует полного safety-цикла:

```text
read-only -> transfer dry-run -> review -> approved -> apply -> verify -> result
```

## Формат отчета по карточке

Подтвержденный владельцем формат от 2026-06-25:

- для визуальной проверки карточки готовить мобильный HTML-отчет;
- HTML должен быть удобен для просмотра в мобильном браузере Telegram:
  крупные читаемые блоки, адаптивная верстка, горизонтальная прокрутка только
  для широких таблиц;
- коллаж всех фото карточки должен быть встроен в HTML или лежать рядом с
  отчетом и быть явно показан вверху отчета;
- структура рекомендаций: `сейчас -> рекомендую -> почему`;
- вверху отчета показывать краткий вывод, статус `read-only/dry-run/apply`,
  приоритет и идентификаторы Ozon/WB;
- отдельными блоками показывать фото-аудит, текущие поля, рекомендации,
  SEO/видимость, группировку, риски, ограничения и решения на согласование;
- если карточка есть на Ozon и WB, показывать обе площадки рядом, но не
  смешивать их разные поля;
- технические источники, raw paths и подробные ограничения можно оставлять в
  HTML-файле, а Telegram-сводку держать короче;
- перед отправкой HTML владельцу агент обязан сам открыть отчет в браузере и
  проверить мобильный `390x844` и десктопный `1366x1000` viewport; мобильный
  `scrollWidth` должен совпадать с `clientWidth`, иначе разметку нужно
  исправить до отправки;
- для первой подтвержденной карточки-прототипа использовать как ориентир файл:
  `data/runs/2026-06-24/card_agent_audit_20260624/cards/0001_chev_back_fsb_text0001/audit_mobile.html`.

Для каждой карточки использовать структуру:

1. Краткий вывод.
2. Источники и идентификаторы:
   - marketplace;
   - `offer_id`/`sku` или `vendorCode`/`nmID`;
   - ссылка/ID карточки;
   - дата snapshot.
3. Фото-аудит.
   - приложенный коллаж всех фото карточки;
   - недостающие фото и задачи дизайнеру, если есть.
4. Текущие поля карточки:
   - название;
   - описание;
   - хештеги;
   - характеристики;
   - цвет и название цвета;
   - материал/состав;
   - размер/вес/упаковка;
   - цена продавца;
   - витринная цена из parser, если есть;
   - остаток;
   - группа `model_id`/`imtID`.
5. SEO и выдача:
   - целевые запросы;
   - ключевые запросы, по которым карточка уже видна в parser/Ozon;
   - позиции;
   - конкуренты;
   - цена top-10/top-30.
6. Риски.
7. Предлагаемые изменения.
8. Что нужно согласовать.

В отчете рядом показывать текущие и рекомендуемые значения:

```text
Параметр | Сейчас | Рекомендую | Пояснение
```

После внесения любых изменений отчет пересобирается полностью и снова
отправляется владельцу файлом и в чат. В post-apply/verify отчете показывать:

```text
Параметр | Было | Стало | Решение владельца / причина
```

Отдельно указывать:

- какие рекомендации владелец принял;
- какие отменил;
- какие изменил своим решением;
- что фактически изменено в карточке;
- что осталось в backlog.

## Telegram-вывод по карточке

Вместе с файлом отчета агент обязан дать в чат полноценный, но не перегруженный
вывод по карточке. В чате не указывать источники, API-методы, raw paths и
другую техническую информацию, если это не нужно для решения владельца. Эти
детали остаются в файле.

Предварительный аудит до apply:

1. Заключение аудита карточки.
2. Полная информация по карточке в формате `сейчас -> рекомендую`:
   название, описание, фото, хештеги, цвет, название цвета, материал/состав,
   размер, вес, упаковка, TNVED, цена/остаток, группа.
3. SEO-видимость: список ключевых запросов, по которым карточка уже найдена
   parser/Ozon, и краткие метрики видимости. Этот блок нельзя убирать из
   Telegram-вывода по карточке, потому что от него зависит подбор названия и
   хештегов.
4. Пояснение рекомендаций.
5. Что нужно согласовать.
6. Файл отчета и коллаж фото.

После apply/verify:

1. Результат аудита после изменений.
2. `Было -> стало` по каждому измененному параметру.
3. Какие рекомендации владелец принял.
4. Какие рекомендации отменил.
5. Что владелец изменил своим решением.
6. Что осталось сделать.
7. Файл отчета и коллаж фото.

## Запреты

- Не предлагать правку названия, описания или характеристик без просмотра всех
  фото.
- Не выдумывать камуфляж, размер, материал, код, смысл изображения или
  комплектацию.
- Не смешивать шевроны с липучкой и пришивные нашивки.
- Не применять изменения без отдельного подтверждения владельца.
