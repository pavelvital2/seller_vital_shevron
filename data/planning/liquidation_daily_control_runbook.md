# Ежедневный контроль распродажи Ozon и WB

Статус: `implemented`, 2026-07-31.

## Назначение

Штатная задача `liquidation-daily-control` ежедневно контролирует точные
owner-approved когорты:

- Ozon: `138` SKU из сохраненного liquidation plan;
- Wildberries: `163` nmID из сохраненного liquidation plan.

Таймер ставит задачу в SQLite Job Worker, а не отправляет текстовое
напоминание. Ключ даты дедуплицирует повторную постановку.

## Контракт

Отчет использует только завершенные дни и для каждого товара сохраняет строку,
включая нулевые показы, клики и заказы. Seller/Statistics API заказы считаются
отдельно от рекламной атрибуции.

Hard stop:

- Ozon: CPC-расход `50 руб. * pack_qty` без Seller API заказа;
- WB: `10` кликов или `20 руб.` CPC-расхода без Statistics API заказа.

Достижение порога создает `stop_review.json` с `actions_checksum`. Это не
разрешение на изменение кампании. Автоматическое отключение CPC, изменение
цен, minimum, акций или ставок запрещено.

Товар включается в новый stop-review только если одновременно достигнут
hard-stop и он всё ещё состоит в активной CPC-кампании. Исторический расход
сохраняется, но уже исключенная строка получает
`hard_stop_already_inactive` и повторно не предлагается к apply.

После отдельного согласования используется runtime-цепочка
`liquidation-stop-plan -> liquidation-stop-apply -> liquidation-stop-verify`.
Plan заново подтверждает активные кампании и membership, apply удаляет только
exact Ozon SKU/WB nmID, а verify требует отсутствия всех согласованных строк.
Состав и ставки остальных товаров кампании сверяются до и после операции.

Для Ozon stop-review обязан хранить оба стабильных идентификатора раздельно:
`product_id` карточки и рекламный `ozon_sku`. Подмена `product_id` значением
SKU запрещена; фактическое исключение из CPC выполняется по `ozon_sku`, а
карточка и актуальный `offer_id` сверяются по `product_id`.

## Источники участия в продвижении

- Ozon Elastic определяется по актуальному массиву
  `marketing_actions.actions`; поле `marketing_actions.current` используется
  только как fallback для старого формата ответа.
- WB CPC определяется по составу кампаний: `adverts[].nm_settings[]` и
  положительная поисковая ставка. Нельзя определять участие только по строкам
  рекламной статистики: товар без показов может отсутствовать в статистике, но
  оставаться в кампании.
- Отчет обязан показывать покрытие точной когорты: Ozon Elastic, Ozon CPC и WB
  CPC. Нулевые рекламные строки сохраняются.

Правило подтверждено повторным read-only запуском
`liquidation_daily_control_20260801T_corrected_analysis`: Ozon Elastic
`120/138`, Ozon CPC `122/138`, WB CPC `163/163`.

## Управленческий формат отчёта

С 2026-08-02 краткая техническая сводка заменена управленческим отчётом. Он
обязан отвечать не только на вопрос о hard stop, но и показывать:

- сколько SKU получили хотя бы один seller-заказ и какую долю точной когорты
  они составляют;
- заказанные товары и физические изделия по `pack_qty`, оборот заказов,
  CPC-расход и расход на seller-заказ;
- дневную рекламную воронку `показы -> клики -> корзина -> рекламные заказы`;
- отдельные группы решений: продажи есть, клики без продаж, показы без кликов,
  нет видимости, нет релевантного запроса, нет остатка, stop-review и
  недостаточный период контроля;
- текущую parser-видимость точной когорты по релевантным запросам: статус,
  лучшую позицию, число видимых/релевантных запросов и регионы видимости;
- конкретную read-only рекомендацию по каждому SKU и фильтры в HTML.

Релевантность запроса определяется по назначению товара, а не по факту
случайного появления в выдаче. Товар без подходящего запроса в пакете должен
получить `query_pack_gap`, а не ложную нулевую видимость. Наличие в регионе
остаётся отдельной возможной причиной видимости и не включается в саму метрику.

Контрольный отчёт:
`data/runs/2026-08-02/liquidation_management_review_20260802T085122/`.
Parser warehouse: срез `2026-07-30`, Ozon `2` региона, WB `4` региона,
пакет `shevron-core`, точные ownership-фильтры.

Исправлена дата Ozon Performance API: строки отчёта могут приходить как
`DD.MM.YYYY`, тогда как внутренний дневной индекс использует `YYYY-MM-DD`.
Без нормализации агрегат за период был верным, но дневные Ozon-строки
становились нулевыми. Regression-тест проверяет локализованную дату.

## Стабильная идентификация Ozon

С 2026-08-03 `offer_id` нельзя использовать как ключ мониторинга распродажи:
артикул продавца изменяем и может отличаться от артикула, сохранённого в
исходном плане. Обязательные ключи:

- цены и остатки связывать по стабильному `product_id`;
- заказы продавца и рекламу связывать по Ozon SKU;
- текущий `offer_id` получать из свежего Seller API и использовать только для
  отображения;
- перед любым новым решением по остановке рекламы пересобирать саму когорту из
  полного живого каталога: FBO-остаток больше нуля и ноль завершённых выкупов
  за согласованные 30 завершённых дней;
- старую фиксированную численность когорты нельзя использовать как входной
  фильтр: смещение 30-дневного окна меняет состав независимо от дрейфа
  артикулов.

Контрольный пересбор `2026-07-04 - 2026-08-02` дал `142` SKU: `128` строк
остались из старой когорты `138`, `10` выбыли из-за завершённых выкупов и `14`
вошли заново. Источник:
`data/runs/2026-08-03/ozon_dormant_cohort_rebuild_20260803T172401/`.

## WB второй ценовой шаг

`wb-liquidation-stage2-plan` читает свежие WB цены только для `18` строк с
`requires_second_price_stage=true`, проверяет текущую скидку, цену и
распродажный floor и выпускает `pending_approval.json`. Upload не выполняется.

После owner approval используется только Job Worker задача
`wb-liquidation-stage2-apply`. Она выполняет scoped WB preflight, строит новый
fresh-план и требует полного совпадения checksum и payload с согласованным
планом. При любом drift upload запрещён. Разрешён один официальный upload
скидок; повторная запись без нового плана и approval запрещена. Базовая цена и
минимальная цена сохраняются без изменения. Успех подтверждается как историей
upload, так и свежим Prices API по каждой строке; отдельная read-only задача
`wb-liquidation-stage2-verify` доступна для recovery.

Подтверждённый запуск 2026-08-01:

- plan: `wb_liquidation_stage2_plan_20260801T150359`;
- apply: `wb_liquidation_stage2_apply_20260801T150526`;
- Job: `job_wb-liquidation-stage2-apply_20260801T120427Z_866af36d`;
- upload ID: `181544452`;
- drift: `0`; WB принял `17/17`; Prices API подтвердил `17/17`;
- у всех 17 строк изменена только скидка, базовая цена `2100 руб.` и minimum
  не менялись;
- runtime approval закрыт после `apply -> verify`.

Исторический результат этапа нельзя определять только сравнением текущей
скидки с исходной целью. Если более поздняя owner-approved операция изменила
скидку, отчет показывает `applied_then_overwritten`, а не ложный
`pending_stage2`. Для подтвержденного этапа 2026-08-01 исторически завершены
все `18/18`: `17` строк загружены и проверены, одна уже находилась на цели.

После подтвержденного восстановления полной Ozon ценовой сетки запуском
`ozon_full_price_grid_restore_apply_20260803T195149` исходные ликвидационные
minimum являются `superseded_plan_reference`. Расхождение с ними сохраняется
для аудита, но не считается актуальной ошибкой и не является основанием
понижать minimum.

Новый контрольный отсчёт для этих 17 товаров начинается
`2026-08-01 15:05:26 МСК`. Не принимать решение об остановке CPC по ранним
неполным суткам. Первый вывод после двух полных дней `2026-08-02` и
`2026-08-03` формируется ежедневным контролем `2026-08-04 09:00 МСК`.
