# План кнопки «Цены и маржа»

Дата фиксации обсуждения: 2026-07-18.

Статус: `v1_ozon_read_only_implemented`, marketplace write не реализован.

## Реализованный первый вариант Ozon

На 2026-07-18 реализован read-only сценарий `Ozon -> Цены и маржа`:

1. владелец выбирает финансовый период `15` или `30` завершенных дней;
2. вводит себестоимость и целевую маржу одного физического изделия;
3. Telegram ставит `ozon-pricing-margin` в Job Worker;
4. задача читает Ozon FBO finance transactions, текущие цены/комиссии и
   подтвержденный `pack_qty` единого каталога;
5. в чат возвращается краткая сводка, отдельно расходы на проданный
   товар/комплект и физическое изделие;
6. прикладывается Excel с расходами, сеткой по `pack_qty` и сопоставлением с
   текущими Ozon-ценами.

Задача использует только полные дни до вчерашнего включительно. Если нет
завершенных продаж, текущей комиссии FBO или доля удержаний делает расчет
невозможным, ценовая сетка блокируется. Первый вариант не сохраняет новую
себестоимость как политику, не создает dry-run изменений и не вызывает price
write endpoints Ozon.

Технические точки:

- `src/seller_agent/tasks/ozon_pricing_margin.py`;
- `src/seller_agent/tasks/registry.py`;
- `src/seller_agent/core/workflow_runner.py`;
- `src/seller_agent/bot/runtime_jobs.py`;
- `src/seller_agent/bot/commands.py`;
- `tests/test_ozon_pricing_margin.py`.

## Цель

Добавить в Telegram-бот отдельный управляемый контур расчета и последующего
изменения цен Ozon/WB:

- внутренней себестоимости физического изделия;
- минимальной цены;
- обычной цены со скидкой;
- базовой цены до скидки.

Расчет должен обеспечивать заданную владельцем рублевую маржу на каждое
физическое изделие с учетом фактических расходов площадки. Для комплектов
себестоимость и маржа умножаются на `pack_qty`, а средняя логистика относится
к одному проданному товару/комплекту.

## Согласованная основа расчета

Для товара с `pack_qty = n`:

```text
cost_total = cost_per_physical_item * n
target_margin_total = target_margin_per_physical_item * n
minimum_price =
  (cost_total + target_margin_total + fixed_cost_per_order)
  / retained_price_share
```

Где:

- `fixed_cost_per_order` - подтвержденные фиксированные расходы на один
  проданный товар, прежде всего средняя логистика;
- `retained_price_share = 1 - variable_expense_rate`;
- налог не включается по действующему правилу владельца;
- реклама и прочие расходы не добавляются повторно, если они уже вошли в
  рассчитанную эффективную долю расходов.

`pack_qty` брать только из подтвержденного внутреннего каталога/паспорта, не
определять по названию карточки. Две неразрезанные петлицы считаются одним
физическим изделием.

## Резерв 20% для дополнительной акции

Если цена по акции может быть на 20% ниже обычной цены со скидкой и при этом
не должна опускаться ниже минимальной цены:

```text
minimum_price = discounted_price * 0.80
discounted_price = minimum_price / 0.80
```

Следовательно, обычная цена со скидкой должна быть на 25% выше минимальной.
Пример: `minimum_price=500`, `discounted_price=625`, цена после дополнительной
скидки 20% равна `500`.

## Базовая цена

Чтобы без дополнительной акции покупатель видел скидку 50%, базовая цена
считается от обычной цены со скидкой:

```text
base_price = discounted_price / (1 - 0.50)
base_price = discounted_price * 2
```

Расчет базовой цены только от будущей акционной цены не гарантирует скидку 50%
в обычном состоянии. Показ зачеркнутой цены дополнительно зависит от правил и
проверок площадки, поэтому после изменения нужен marketplace verify.

## Источник расходов

Расходы считаются отдельно для Ozon FBO и WB FBW. Нельзя использовать одну
общую модель на обе площадки.

Для каждого расчета рекомендуется получать два среза:

- 30 дней - стабильная основа;
- 15 дней - контроль свежих изменений.

В отчете показывать по каждому срезу:

- период и дату свежести;
- число завершенных продаж в выборке;
- переменную долю расходов;
- среднюю фиксированную логистику на один проданный товар;
- общие расходы маркетплейса на один проданный товар/комплект;
- расходы маркетплейса в пересчете на одно физическое изделие;
- включение рекламы, хранения, приемки и возвратной логистики;
- рассчитанную минимальную цену.

Расходы на одно физическое изделие рассчитывать так:

```text
marketplace_expenses_per_sold_product =
  commission
  + acquiring
  + logistics
  + storage_and_acceptance
  + allocated_return_logistics
  + advertising
  + other_confirmed_marketplace_expenses

marketplace_expenses_per_physical_item =
  marketplace_expenses_per_sold_product / pack_qty
```

Для одиночного изделия обе суммы совпадают. Для комплекта из двух изделий
логистика и другие расходы одного заказа сначала учитываются на весь комплект,
затем делятся на `2` для owner-facing показателя расходов на одно физическое
изделие. Рядом обязательно показывать `pack_qty`, чтобы деление было
проверяемым.

Бот должен выводить не только итоговую сумму, но и расшифровку расходов на одно
физическое изделие:

| Статья | На проданный товар/комплект | На одно физическое изделие |
| --- | ---: | ---: |
| Комиссия площадки | ... руб. | ... руб. |
| Эквайринг/обработка платежа | ... руб. | ... руб. |
| Логистика | ... руб. | ... руб. |
| Хранение и приемка | ... руб. | ... руб. |
| Возвратная логистика | ... руб. | ... руб. |
| Реклама | ... руб. | ... руб. |
| Прочие подтвержденные расходы | ... руб. | ... руб. |
| **Всего расходов маркетплейса** | **... руб.** | **... руб.** |

Если отдельную статью нельзя надежно распределить по товару или физическому
изделию, бот не должен подставлять ноль. Такая строка показывается как
`не распределено`, сумма и причина выводятся отдельно, а расчет получает
warning.

Основной расчет рекомендуется строить по 30 дням. Если расчетный минимум по
15 дням выше более чем на 5%, бот должен показать предупреждение и предложить
консервативный вариант. При недостаточной выборке расчет помечается
`insufficient_data`, без скрытого применения ненадежного результата.

Среднюю логистику считать взвешенно по завершенным продажам. Отмены и строки
без продажи не включать в знаменатель. Нельзя одновременно включать один и тот
же расход в процент удержаний и фиксированную сумму.

## Telegram-сценарий

Кнопка размещается отдельно в меню каждой площадки:

```text
Ozon -> Цены и маржа
Wildberries -> Цены и маржа
```

Порядок работы:

1. Выбрать область применения: весь ассортимент, одна комплектность
   `pack_qty`, выбранная группа или отдельные SKU.
2. Выбрать основу расходов: 30 дней либо консервативный вариант по срезам
   15/30 дней.
3. Ввести себестоимость одного физического изделия; по умолчанию показать
   последнее сохраненное значение.
4. Ввести желаемую маржу с одного физического изделия.
5. Рассчитать ценовую сетку отдельно по `pack_qty` и площадке.
6. Показать использованную финансовую выборку и расходы маркетплейса: отдельно
   на один проданный товар/комплект и на одно физическое изделие, с разбивкой
   по статьям расходов.
7. Показать минимальную, обычную скидочную и базовую цены, ожидаемую выплату и
   маржу на физическое изделие.
8. Предложить: `Согласовать расчет`, `Изменить исходные данные`, `Изменить
   цены вручную`, `Скачать Excel`, `Отменить`.
9. При ручной корректировке сначала менять сетку по комплектности, затем при
   необходимости задавать исключения для отдельных SKU.
10. Согласование расчета создает только сохраненный dry-run. Оно не меняет
   marketplace state.
11. Перед apply выполнить fresh snapshot, drift-check, проверку акций,
    ограничений площадки и показать финальный diff владельцу.
12. После отдельного подтверждения запустить изменение через Job Worker,
    выполнить verify и отправить итоговый отчет.

Пример owner-facing блока перед ценовой сеткой:

```text
Расходы Ozon за 30 дней
Завершенных продаж: 1 240
Средние расходы на проданный товар: 286,40 руб.
Средние расходы на одно физическое изделие: 251,70 руб.

Комиссия: 176,00 руб./изделие
Логистика: 61,50 руб./изделие
Эквайринг: 8,20 руб./изделие
Хранение и приемка: 3,70 руб./изделие
Возвратная логистика: 2,30 руб./изделие
Реклама: включена в расчет
```

Числа в примере являются только форматом интерфейса, не фактическими данными
магазина.

## Что показывает dry-run перед apply

- количество выбранных и изменяемых товаров;
- повышение, снижение и отсутствие изменений отдельно по каждому полю;
- текущие и целевые цены;
- расходы маркетплейса на проданный товар/комплект и на одно физическое
  изделие с расшифровкой и периодом расчета;
- ожидаемую выплату и маржу на физическое изделие;
- товары в активных акциях и риск выхода из них;
- товары, где текущая акционная цена ниже нового минимума;
- округление и фактическую скидочную цену WB;
- риск ценового карантина WB;
- состояние Ozon-защиты минимальной цены;
- строки с drift, missing mapping, missing `pack_qty` или недостаточными
  финансовыми данными.

## Раздельные подтверждения

Одна кнопка не должна безусловно менять все поля. Разделить решения владельца:

1. сохранить новую внутреннюю себестоимость;
2. применить базовую и обычную скидочную цену;
3. применить минимальную цену;
4. для Ozon отдельно проверить/обновить срок учета минимальной цены в
   автоакциях;
5. для WB использовать только подтвержденный официальный маршрут минимальной
   цены.

Себестоимость хранить как версионируемую внутреннюю политику с датой начала
действия. Ее изменение не является marketplace write. В будущем предусмотреть
SKU-level исключения без перезаписи истории предыдущих расчетов.

## Различия Ozon и WB

### Ozon

- базовая цена: `old_price`;
- обычная цена со скидкой: `price`;
- минимальная цена: `min_price`;
- цена активной акции проверяется отдельно;
- изменение `min_price` само по себе не поднимает уже действующую акционную
  цену;
- состояние 30-дневного учета минимальной цены требует отдельного контроля.

### Wildberries

- API принимает базовую `price` и целочисленную скидку `discount`;
- фактическую скидочную цену нужно пересчитать после округления и показать
  владельцу;
- резкое снижение итоговой цены может попасть в ценовой карантин;
- автоматический write-маршрут минимальной цены не считать подтвержденным до
  отдельной проверки официального API/ЛК/XLSX.

## Обязательные проверки

```text
base_price > discounted_price > minimum_price
discounted_price >= minimum_price / 0.80
expected_action_price >= minimum_price
expected_margin_per_item_at_minimum >= target_margin_per_item
```

Ручное значение, нарушающее расчетную маржу или ценовую связь, не применять
молча. Бот должен показать конкретное нарушение и потребовать отдельного
явного подтверждения исключения.

## Рекомендуемые этапы реализации

1. Read-only калькулятор, финансовая расшифровка, Excel и версионируемая
   внутренняя себестоимость.
2. Ручная корректировка сетки и сохраненный dry-run с quality gates.
3. Ozon apply для `old_price`/`price`/`min_price` через Job Worker.
4. WB apply для `price`/`discount`; минимальная цена только после подтверждения
   безопасного маршрута.
5. Post-apply мониторинг участия в акциях, фактической цены и маржи.

## Открытые решения перед write-этапом

1. Оставить свободный выбор 15/30 дней или автоматически сравнивать оба среза
   и использовать более консервативный минимум.
2. Оставить ли дополнительный акционный резерв строго 20% или сделать его
   изменяемым с default `20%`.
3. Оставить ли целевую видимую скидку строго 50% или сделать ее изменяемой с
   default `50%`.
