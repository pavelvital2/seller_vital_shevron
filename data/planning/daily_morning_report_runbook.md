# Daily Morning Report Runbook

## Команды

Технический отчет:

```bash
PYTHONPATH=src python3 -m takterra_agent.cli daily-morning-report
```

Селлерский v2:

```bash
PYTHONPATH=src python3 -m takterra_agent.cli daily-morning-report --seller-v2
```

Селлерский v3 по утвержденному Telegram-шаблону:

```bash
PYTHONPATH=src python3 -m takterra_agent.cli daily-morning-report --seller-v3
```

## Правило до унификации SKU

Отчет должен показывать Ozon и WB как отдельные контуры. Объединение по товару
разрешено только там, где есть подтвержденный mapping.

Telegram-вывод ежедневного отчета строить по общему стандарту
`data/planning/chat_report_templates.md`: chat-summary должен быть достаточным
для просмотра с телефона без открытия полного файла.

## Обязательный формат ежедневного отчета

Ежедневный отчет строится за одну дату: предыдущий календарный день по
`Europe/Moscow`, период `00:00-23:59`.

Все ключевые блоки должны показывать Ozon и WB рядом:

- заказы за вчера: количество и сумма;
- выкупы за вчера: количество и сумма;
- отмены за вчера;
- отзывы и вопросы за вчера `00:00-23:59`;
- отзывы и вопросы, которые требуют внимания на текущий момент: ответ или
  просмотр;
- Ozon-уведомления/сообщения из `https://seller.ozon.ru/app/messenger?group=customers_v2`:
  - сколько новых/непрочитанных;
  - сколько вопросов/чатов покупателей требуют ответа;
  - сколько важных площадочных уведомлений нужно передать владельцу;
  - кратко: какие изменения Ozon важны;
  - что отсеяно как шум/мусор;
- остатки на текущий момент;
  - для WB не называть отсутствующую строку в legacy stock endpoint нулевым
    остатком; писать отдельно: `WB-артикулы без строки в источнике остатков`;
  - в полном файле отчета показывать WB товары с подтвержденным нулевым
    остатком и отдельную выборку WB-артикулов без строки в источнике остатков
    с названием товара, если оно есть в master catalog;
- акции на текущий момент: какие активны, в каких участвуем, сколько товаров
  участвует, сколько не участвует и почему;
  - причины неучастия/проблем по акциям обязательно раскладывать минимум на:
    `нулевой остаток`, `участие в акции выше порога`,
    `нет акций для этого товара`;
  - для WB `участие в акции выше порога` не смешивать с `не участвует`: это
    товары, которые есть в акциях, но требуют корректировки скидки по схеме;
  - если товар отсутствует в legacy stock endpoint WB, это писать отдельно как
    `нет строки в источнике остатков`, не приравнивать к нулю без
    подтверждения;
- текущие поставки: есть или нет; если есть, показать стадии отдельно для Ozon
  и WB:
  - формируется;
  - готова к отгрузке;
  - на точке отгрузки;
  - в пути;
  - на складе приемки;
  - приемка.

Если источник данных не подключен, вернул ошибку или не дает нужный показатель,
в отчете писать `не подтверждено` и указывать причину. Нельзя подставлять
догадки вместо фактических данных.

Если ежедневный отчет получается неполным из-за недоступного ЛК, слетевшей
сессии или ошибки LK/CDP fallback, агент не должен сразу отдавать неполный
отчет как итоговый. Сначала нужно прямо предложить владельцу восстановить
подключение к соответствующему ЛК и пересобрать отчет. Неполный отчет можно
отправлять только если владелец подтвердил, что отчет нужен сейчас в текущем
неполном виде, либо если восстановление ЛК невозможно в рамках текущего
цикла. В итоговом сообщении обязательно указать, какие блоки остались
`не подтверждено` и почему.

## Источники, которые нужно довести до v3

- Ozon/WB выкупы и отмены за точный период `00:00-23:59`.
- Ozon отзывы/вопросы за вчера и текущие требующие внимания.
- Ozon уведомления/сообщения из Messenger: покупательские вопросы, важные
  сообщения площадки и шум.
- Ozon/WB action participation с причинами неучастия товаров.
- Ozon/WB supply status по стадиям поставки.

До подключения этих источников ежедневный отчет может иметь статус `warning`,
даже если API и сессии работают.

## Реализация v3

`--seller-v3` уже должен:

- считать дату отчета по `Europe/Moscow`;
- использовать предыдущий календарный день как период `00:00-23:59`;
- показывать Ozon/WB рядом в таблицах;
- брать Ozon заказы из Seller API `/v1/analytics/data`;
- брать Ozon выкупы из Seller API `/v3/finance/transaction/list` по операциям
  `OperationAgentDeliveredToCustomer` за дату отчета; не считать выкупы по
  статусу `delivered` из `/v2/posting/fbo/list`, потому что этот метод
  фильтрует отправления, а не факт выкупа за календарный день;
- брать Ozon расходы за вчера из всех операций Seller API
  `/v3/finance/transaction/list` за дату операции: комиссия
  `sale_commission`, логистика и эквайринг из `services`, реклама по операции
  `OperationMarketplaceCostPerClick`, хранение по
  `OperationMarketplaceServiceStorage`, возвраты/отмены/невыкупы по
  `OperationItemReturn`, кросс-докинг по `MarketplaceServiceItemCrossdocking`;
  итог расходов считать как `gross_amount - net_amount` и сверять с
  расшифровкой;
- не использовать `/v1/finance/products/buyout` для обычных покупательских
  выкупов: по официальному обсуждению Ozon for dev этот метод относится к
  товарам, которые Ozon выкупил у продавца, а не к фактическим продажам
  покупателям;
- `/v1/finance/realization/by-day` является более прямым дневным источником
  реализации, но текущий ключ Vital Shevron вернул `HTTP 403: Data is
  available only with a Premium plus subscription`; поэтому в v3 используется
  `/v3/finance/transaction/list`;
- брать Ozon FBO отмены из Seller API `/v2/posting/fbo/list` за период
  `00:00-23:59` MSK только как операционный источник по отправлениям; для
  строгой отмены по дате отмены нужен отдельный проверенный источник;
- брать Ozon остатки из Seller API `/v4/product/info/stocks`;
- брать Ozon отзывы/вопросы сначала из официальных Seller API
  `/v1/review/count`, `/v1/review/list`, `/v1/question/count`,
  `/v1/question/list`; если официальный API недоступен для текущего ключа,
  использовать read-only LK/CDP fallback из `reviews_questions` и явно писать,
  что fallback видит только доступные в ЛК непросмотренные отзывы и новые
  вопросы;
- брать Ozon уведомления/сообщения из Messenger по
  `data/planning/ozon_messenger_runbook.md`: сначала официальный Seller API
  `/v3/chat/list` и `/v3/chat/history`, если их достаточно; если площадочные
  уведомления или UI-фильтры не видны через API, использовать LK/CDP websocket
  fallback; в отчете отделять вопросы покупателей, важные изменения площадки и
  шум;
- брать WB заказы/отмены из Statistics API `/api/v1/supplier/orders` с
  `flag=1`;
- брать WB выкупы/возвраты из Statistics API `/api/v1/supplier/sales` с
  `flag=1`; это оперативный предварительный источник, официально обновляется
  раз в 30 минут, `1 строка = 1 продажа/возврат = 1 товар`;
- в `--seller-v3` не запрашивать WB orders/sales за `today`, если отчет
  строится только за вчера: у Statistics API жесткий лимит, лишний второй
  запрос может привести к `HTTP 429` и потере нужного блока;
- брать WB финансовые расходы за вчера из Finance API
  `/api/finance/v1/sales-reports/list` с `period=daily`; использовать поля
  `retailAmountSum`, `forPaySum`, `deliveryServiceSum`, `paidStorageSum`,
  `paidAcceptanceSum`, `deductionSum`, `penaltySum`,
  `additionalPaymentSum`, `cashback*`, `bankPaymentSum`;
- WB рекламу за вчера брать отдельно из Promotion API `/adv/v3/fullstats`,
  поле `sum`; добавлять как рекламный расход отдельно от отчета реализации и
  явно писать, что рекламный расход не сверен как часть `bankPaymentSum`;
- брать WB отзывы/вопросы за период и текущие требующие внимания из
  Customer Communication API;
- брать сводку по акциям из последних read-only/dry-run Ozon Elastic и WB
  actions reports;
- для причин по акциям читать детальные CSV последнего Ozon Elastic dry-run и
  WB actions dry-run:
  - Ozon `reason_code=no_stock` -> `нулевой остаток`;
  - Ozon `reason_code=below_min_price_threshold` -> `участие в акции выше
    порога/не проходит порог цены`;
  - WB `Акций=0` -> `нет акций для этого товара`;
  - WB `Причина` содержит `порога >` -> `участие в акции выше порога`;
- писать причины неучастия в акциях понятным русским текстом, без внутренних
  кодов вроде `skip_candidate` или `outside_promos`;
- писать `не подтверждено` для блоков без проверенного read-only источника.

Подтвержденное ограничение WB Statistics API: при `flag=1` метод возвращает
заказы или продажи за дату, равную `dateFrom`; время в `dateFrom` не важно.
Источник: официальная документация WB API, раздел Main Reports.

Официальные источники WB:

- Main Reports: `https://dev.wildberries.ru/docs/openapi/reports`;
- Financial Reports: `https://dev.wildberries.ru/docs/openapi/financial-reports-and-accounting`;
- Promotion API: `https://dev.wildberries.ru/docs/openapi/promotion`.
