# Checkpoint анализа распродажи Ozon и Wildberries

Статус: `owner_deferred`, сохранено 2026-08-01.

## Назначение

Документ сохраняет подтвержденный read-only анализ распродажи и рекомендации,
к которым владелец решил вернуться позже. Он не является approval на изменение
цен, minimum, акций, ставок, бюджетов или состава кампаний.

## Период и источники

- период: `2026-07-30 - 2026-07-31`, только завершенные дни;
- текущий неполный день исключен;
- заказы: Ozon Seller API и WB Statistics API;
- реклама: Ozon Performance API и WB Promotion API;
- акции, цены и остатки: свежие marketplace API данные;
- исправленный контроль:
  `data/runs/2026-08-01/liquidation_daily_control_20260801T_corrected_analysis/`;
- WB второй ценовой шаг:
  `data/runs/2026-07-31/wb_liquidation_stage2_plan_20260731T223733/`.

Рекламная атрибуция не заменяет marketplace seller orders. Для оценки
результата распродажи основная метрика - seller-order units, а рекламные
заказы сохранены отдельно.

## Сохраненные рекомендации

1. Первым следующим write-шагом после нового owner approval выполнить fresh
   preflight и применить второй ценовой этап WB для `17` товаров, затем
   проверить цены и участие в акциях.
2. Не повышать массово ставки WB: все `163` товара уже находятся в CPC.
3. После применения финальной цены начать для `18` товаров новый контрольный
   период `48 часов`.
4. WB `707892598` сначала проверить по финальной цене. Если после нового окна
   он снова наберет `10` кликов или `20 руб.` расхода без seller-order unit,
   подготовить отдельное отключение CPC на согласование.
5. На Ozon сохранить текущие ставки, Elastic и состав CPC до получения
   минимум трех полных дней наблюдения.
6. Не форсировать `18` Ozon SKU без Elastic: ранняя контрольная группа уже
   дала `3/9` seller-order units всей когорты.
7. После семи полных дней товары без заказов при финальной цене вывести из
   платного продвижения либо подготовить отдельный dry-run окончательной
   убыточной распродажи. Ниже утвержденного floor автоматически не опускаться.

## Точка продолжения

1. Собрать fresh `liquidation-daily-control` только по завершенным дням.
2. Сравнить накопленные `3/7` полных дней с этим checkpoint.
3. Перестроить `wb-liquidation-stage2-plan`, проверить drift и checksum.
4. Показать владельцу точные `17` строк и ожидаемые цены.
5. Выполнять `apply -> verify` только после нового явного согласования.

До возврата владельца ежедневный read-only контроль продолжает работать.
Marketplace write по этому checkpoint не выполнялся.
