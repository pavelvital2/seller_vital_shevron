## 2026-06-10 — Product-first архитектура TAKTERRA для Ozon и WB

Вопрос владельца:

Подготовить единый проект управления магазинами TAKTERRA на Ozon и Wildberries.
Продукция единая, внутренние артикулы одинаковые для обоих маркетплейсов.

Рекомендация:

Центром структуры должен быть не маркетплейс, а наш товар. Ozon и WB должны
рассматриваться как каналы продаж одного master catalog.

Целевая модель:

```text
наш товар / master_sku
├─ Ozon: offer_id, product_id, sku, barcode, карточка, цена, остатки, акции
└─ WB: vendorCode, nmID, barcode, subjectID, карточка, цена, остатки, акции
```

Целевое правило артикула продавца:

```text
master_sku == Ozon offer_id == WB vendorCode
```

Влияние на проект:

- `data/catalog/processed/master_catalog.*` становится центральным рабочим
  слоем для сверки Ozon/WB.
- Любая задача должна по возможности работать через `master_sku`, а не только
  через `product_id`, `sku`, `nmID` или marketplace-specific identifiers.
- Ручной mapping допустим только как временный диагностический слой, если
  фактические данные API временно не соответствуют целевому правилу.

Статус:

`implemented`. API-сверка подтвердила 203/203 совпадения по единому артикулу
после доведения 5 карточек на WB.

## 2026-06-10 — Единый бот как диспетчер задач

Вопрос владельца:

Объединить опыт трех проектов и подготовить план реализации единого бота
управления двумя магазинами TAKTERRA.

Рекомендация:

Проектировать не склад скриптов и не монолитного Telegram-бота, а диспетчер
задач:

```text
Telegram / chat
  -> dispatcher
  -> task registry
  -> approval guard
  -> lock manager
  -> marketplace adapter
  -> task result/report
```

Бизнес-логика должна жить в task-модулях и marketplace adapters, а бот должен
быть тонким интерфейсом: принять команду, проверить риск, запросить
подтверждение, запустить задачу и отправить отчет.

Влияние на проект:

- Текущий слой `src/takterra_agent/tasks/` должен стать основой будущего task
  registry.
- `src/takterra_agent/marketplaces/ozon/` и
  `src/takterra_agent/marketplaces/wb/` должны изолировать API- и ЛК-специфику.
- `src/takterra_agent/bot/` должен подключаться только к стабильным задачам,
  которые уже отработаны агентом через CLI/report workflow.

Статус:

`accepted`. Начальная структура проекта уже создана вокруг agent/task-runner,
а не вокруг кнопок бота.

магазинами; операции с самими магазинами нужны как сопутствующие действия, на

  выполнена, инструкция дополняется описанием ситуации и способом решения.
- Агент обязан оценивать, можно ли действие оптимизировать или автоматизировать,
  и предлагать рекомендации владельцу на согласование.

Статус:

`accepted`. Правило перенесено в `AGENTS.md` и применяется к операциям WB/Ozon.

## 2026-06-10 — ЛК Ozon/WB как локальный session-контур

Вопрос владельца:

Подключить личные кабинеты Ozon и WB, сделать автоматический refresh/keepalive,
обновлять cookies/state при успешном входе и не терять сессию.

Рекомендация:

Держать ЛК как отдельный локальный session-контур проекта TAKTERRA:

```text
.sessions/ozon/chrome-profile/
.sessions/ozon/ozon_seller_storage_state.json
.sessions/ozon/session_refresh_logs/
.sessions/wb/browser-profile/
.sessions/wb/wb_storage_state.json
.sessions/wb/session_refresh_logs/
```

Секретные данные не выводить в отчеты, инструкции и сообщения. Старые проекты
использовать как read-only источник модели подключения, а перенос профиля или
state делать только по явному разрешению владельца.

Влияние на проект:

- Session-скрипты должны жить в `scripts/sessions/`.
- Порядок подключения и восстановления фиксируется в
  `data/planning/lk_connection_runbook.md`.
- Карты ЛК Ozon/WB обновляются при обнаружении новых ссылок, разделов или
  нюансов входа.

Статус:

`implemented`. Ozon подключен через persistent profile + CDP keeper/watchdog,
WB подключен через новый локальный persistent profile, активный продавец WB
подтвержден как `ИП Рантусова`.

## 2026-06-10 — Safety-контур для опасных операций

Вопрос владельца:

Как безопасно выполнять операции, которые могут менять цены, карточки, акции,
рекламу, остатки или ответы покупателям?

Рекомендация:

Для опасных операций обязательна цепочка:

```text
read-only -> dry-run -> review -> approved -> apply -> verify -> result
```

Apply должен быть невозможен без явного подтверждения владельца или
утвержденного approved-файла.

Влияние на проект:

- Все write-задачи должны иметь dry-run отчет.
- В `data/pending/`, `data/approved/`, `data/locks/` должны храниться
  артефакты safety-контура без секретов.
- Будущий бот должен показывать владельцу краткое резюме риска до apply:
  что меняем, сколько строк, какой payload, как проверяем результат.

Статус:

`accepted`. Правило закреплено в `AGENTS.md` и используется как обязательный
архитектурный контур.

## 2026-06-10 — Дорожная карта к единому проекту управления магазинами

Вопрос владельца:

Какими шагами идти к главной цели: единому проекту управления Ozon и
Wildberries TAKTERRA с будущим ботом.

Рекомендация:

Идти не через быстрые кнопки бота, а через последовательные вертикальные
сценарии:

```text
проверенная операция агента
  -> task-runner
  -> read-only/dry-run отчет
  -> approved/apply при необходимости
  -> verify
  -> инструкция
  -> кнопка бота
```

Рабочие этапы:

1. Закрепить фундамент: master catalog, ЛК-сессии, карты, инструкции, отчеты,
   правила агентов.
2. Довести task-runner до единого стандарта задач: task registry, run_id,
   входные параметры, результат, markdown/json отчеты.
3. Формализовать safety-контур: pending/approved/locks, запрет apply без
   подтверждения, понятный отчет риска.
4. По одному добавлять стабильные read-only сценарии: статус ЛК, статус API,
   сверка каталога, остатки, цены, акции, отзывы/вопросы.
5. Для каждой операции сначала делать dry-run и инструкцию, затем apply только
   после подтверждения владельца.
6. После стабилизации сценария подключать его к Telegram-боту как кнопку или
   команду.
7. Перейти к регулярной автоматизации: расписания, keepalive, ежедневные
   проверки, уведомления о проблемах, рекомендации агента.

Рекомендуемый ближайший технический шаг:

```text
Сделать единый preflight/status слой проекта:
- проверка Ozon API;
- проверка WB API;
- проверка Ozon LK session/keeper;
- проверка WB LK session;
- проверка актуальности master catalog;
- единый отчет status.md/json.
```

Почему именно он:

- это безопасный read-only сценарий;
- он станет основой будущей команды `/status`;
- перед любыми ценами, акциями, карточками, отзывами и рекламой проект должен
  понимать, что API, ЛК и каталог находятся в рабочем состоянии.

Влияние на проект:

- Следующая задача должна укрепить общий каркас, а не начинать новую опасную
  бизнес-операцию.
- После `status/preflight` можно выбирать первый прикладной сценарий:
  отзывы/вопросы, акции, цены или реклама.
- Каждая новая операция должна завершаться обновлением runbook и, при
  необходимости, архитектурных заметок.

Статус:

`implemented_partial`. Первый слой дорожной карты реализован как сценарий
`status-preflight`: Ozon API, WB API, master catalog, Ozon/WB ЛК-сессии и единый
отчет. Первый полный запуск выявил блокер Ozon ЛК `Login required`, при этом WB
ЛК, API и master catalog проверены успешно.


- В safety-контуре нужно хранить reviewed payload и делать drift-check перед
