# API Documentation Registry

Дата создания: 2026-06-28.

## Назначение

Этот каталог хранит проектный слой API-документации Ozon/Wildberries:

- ссылки на официальные источники;
- локальные копии официальных OpenAPI/Swagger-схем, если они доступны для
  скачивания;
- краткие проверенные карточки endpoint-ов, которые используются в проекте;
- историю проверки актуальности;
- заметки о несовпадениях документации и фактического API.

Цель - чтобы агент работал по документации, а не методом подбора параметров.

## Правило источников

При работе с API порядок источников такой:

1. Официальная документация Ozon/WB.
2. Официальная OpenAPI/Swagger-схема или changelog.
3. Уже реализованный и проверенный проектный адаптер.
4. Минимальный read-only smoke-test.
5. Подбор параметров только если документация недоступна, отсутствует, явно
   устарела или противоречит фактическому API.

Перед подбором нужно записать:

- какой официальный источник искали;
- почему он не дал контракт;
- какой read-only запрос выполняется;
- почему запрос безопасен.

## Что сохранять

Разрешено сохранять:

- OpenAPI/Swagger JSON/YAML из официального источника;
- changelog или ссылку на changelog;
- карточку endpoint-а в Markdown;
- дату проверки;
- пример request/response без секретов, персональных данных и закрытых
  коммерческих данных;
- результаты smoke-test в `data/runs/<date>/.../raw/` без секретов.

Не сохранять:

- API-ключи, токены, cookies, storage state, auth headers;
- raw HTML больших страниц без необходимости;
- персональные данные покупателей;
- закрытые финансовые данные в справочных документах;
- длинные дословные копии документации, если достаточно ссылки и выжимки
  контракта.

## Структура

```text
data/reference/api_docs/
  README.md
  ozon/
    README.md
    endpoints/
  wb/
    README.md
    endpoints/
```

Рекомендуемый файл endpoint-а:

```text
<marketplace>/endpoints/<api_area>_<method_name>.md
```

Например:

```text
ozon/endpoints/supply_order_list.md
wb/endpoints/supplies_list.md
```

## Формат карточки endpoint-а

```markdown

Дата проверки: YYYY-MM-DD
Статус: draft/verified/stale
Официальный источник: <URL>

## Что обновлять при изменении
```

## Регулярная проверка

- При добавлении нового API-метода: создать или обновить карточку endpoint-а.
- При изменении API-кода/адаптера: сверить карточку endpoint-а.
- Перед задачей, где API-контракт критичен для write/dry-run: проверить дату
  последней проверки и официальный changelog.
- Минимальная регулярность ревизии API-документации: раз в месяц или раньше,
  если маркетплейс прислал уведомление/новость об изменениях.

Если документация изменилась, нужно обновить:

- карточку endpoint-а;
- профильный runbook в `data/planning/`;
- проектный skill, если изменение влияет на повторяемый workflow;
- `data/planning/project_map.md`, если появились новые важные API-разделы;
- `data/planning/recommendations_index.md`, если нужна автоматизация проверки.
